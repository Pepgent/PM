# D16 v2 发散压力测试报告

v2 补齐了路径白名单，但多数新冲突仍然存在。原因在于 D16 用两个维度安排工作，两者没有对齐：

- **路径维度**：D16-09 给每个席位划了一份路径白名单。
- **时间维度**：D16-10 规定一个席位的全部任务合入 `main` 后立即 `tern kill`。

至少有四类交付物要跨席位协作，或者不能按席位在队列中的顺序完成：根文件、DIST-02、D14-02 的各个调用入口、D16-05 的三步。按路径分给一个席位，解决不了“谁先、谁后、由哪个 issue 承载”的问题。

**替代方案：** 在 D16 中增设一张“跨席位交付物表”。每行写明四项：承载的 issue、执行席位、前置条件、在该席位任务序列中的位置。路径白名单只管写入权限，任务顺序由这张表决定。
- 好处：下面第 3 到第 7 条大多会随之闭合。
- 代价：D16 要多一张表，还要同步扩充 A2，因为 D16-06③ 现在禁止在表外新建 issue。

第二个整体性问题与用户最新一条请求直接相关，放在第 1 条。

## 2. D16-12 的合并锚点：重新造成 U30 所说的互相等待，并且没有合法的触发渠道

### 2a. 没有合法渠道

**分类：主路径失效反例**

  - C4-1 规定常规状态只写 issue 或 PR，并且严禁主会话向双核发送无实质内容的回执（`LEDGER.md:49`）。

- 反例：W-07 开出 SOR-09 的 PR，并在正文附上 LEDGER 核对表。
  - 没有任何合规动作能唤醒双核。

### 2b. 与 D16 自己恢复的 D10-08 冲突

**分类：主路径冲突**

- D10-08 的取舍列明确否决了一个备选：“一切实现细节都上报：回到 U30 的互相等待”（`pepgent-pm/evidence/decisions/D10-repo-delivery.md`，D10-08 行）。
- D10-08 还规定，在已通过的契约范围内，单仓私有实现由工程师决定。
- D16-01 恢复了 D10-08（`D16.md:22`）；D16-12 却要求每个 PR 都由领导层确认，同一份 D16 前后矛盾。

## 3. W-07 与 W-08 的边界

### 3a. 根 `package.json` 和 `bun.lock` 由各工作区共同决定，不能只由一个席位拥有

**分类：主路径失效反例**

- 根 `package.json` 的 workspaces 是 `packages/*` 和 `e2e`（`package.json:5-8`），`bun.lock` 由三个路径域的 manifest 共同生成。
- D16-09 把这两个文件只交给 W-07（`D16.md:30`）。
- 反例：W-07 属于第 1 波，完成后立即被 kill（`D16.md:31`）。W-08 最后启动，给 `e2e/package.json` 加测试依赖时必须更新 `bun.lock`，但 `bun.lock` 的拥有者已经不在了。W-06 改 `packages/store/package.json` 的依赖时也是同样的情况。W-06 的 STO-12 是否真需要新依赖，属于推测。
- D16-09 写着“这三个根文件属于仓 B 的发行文件，D10-02”，这是对 D10-02 的误读。D10-02 的 how 写的是：
  - 仓 B **另有自己的**根 `package.json`、lockfile、`README.md`；
  - `Pepgent/soroi` 的根 `package.json` 保留下来，workspaces 只剩 `e2e`。
  - 因此迁仓以后，soroi 的根文件应归 W-08 一侧。

**替代方案：** 写一条规则：哪个席位改了工作区 manifest，就由它在同一个 PR 里重新生成 `bun.lock`。根 `package.json` 的 `exports`（D16-05②）仍单独交给 W-07。
- 代价：并行 PR 会在 lockfile 上出现机械冲突，rebase 后重新生成即可。

### 3b. `compose/` 下有两个文件没有 owner

**分类：主路径缺口（低）**

- `compose.yaml:84-88` 还引用了 `./compose/startup.yml`，这个文件不在任何席位的白名单里。
- `compose/README.md` 描述了 entrypoint 的行为：第 59 行写“The entrypoint finishes extraction and installation before exec”，第 106 行写发行导入由其实现方负责。A2-05 改动 entrypoint 之后，这份 README 没有人负责更新。
- 建议：把 `compose/**` 整体写进一个席位。

### 3c. 迁仓之后 entrypoint 的归属

**分类：非阻断建议**

- 把 entrypoint 交给 W-07 有依据：D14 的派发影响表本来就把它交给插件工程师（`D14-release-identity.md:36`）。
- 但 D10-02 规定迁仓后 `compose/` 留在 `Pepgent/soroi`，不进仓 B。D16 应补一句：迁仓后 `compose/**` 改由 W-08（soroi 一侧）负责。

### 3d. DIST-02（#224）和 PR260 横跨两个路径域，W-07 可能永远无法退役

**分类：主路径失效反例**

- PR260 的分支是 `eng/install-check-224`，也就是 DIST-02。相关安排如下：
  - GR 把 #260 的接续交给 W-08（`phaseB-review-governance.md:129`）。
  - D10-04④ 规定其中 `scripts/build-release.py` 的部分按仓 B 新布局重写，属于 W-07。
  - D8 中 DIST-02 依赖 E2E-02，而 E2E-02 是 W-08 的工作（`D8-mvp-scope.md:314`、`:375`）。

- 反例：如果 #224 进了 W-07 的切片清单，它要等 E2E-02 完成，而 W-08 要等 W-07 全部合入才启动，两边互相等待。W-07 永远不会“全部合入”，一直占着 3 个名额中的 1 个。
