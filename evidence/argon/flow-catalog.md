## 一、完整独立 omp 定制安装与 AI 逐步 `eval` 消费循环（F01–F03）

### F01：完整独立 soroi omp 定制加载与 `soroi_eval` 根 atom 定义及 `stop` 结束运行【定】
- **一句话的用户可观察结果：** 在不修改 omp 宿主源码且不依赖 `omomp` 的前提下加载完整独立的 soroi omp 定制（插件、扩展、设置、agent 定义、技能、规则），主 agent 调用 `soroi_eval` 正式运行一步定义根 atom 并调用 `stop`，store 创建运行记录、写入 atom 与停止记录，所有末端 atom 停止后运行标记为 `run_end`。
- **从触发到结束的步骤（主路径）：**
  1. 启动加载了完整独立 soroi 定制包（含 `omp-soroi-eval` 与 `omp-soroi-subagent`）的中心主机 `omp` 会话。
  2. 主 agent 调用 `soroi_eval`（`mode: "formal"`），提交包含 `const temp_2200c = 2200` 与 `stop(temp_2200c)` 的代码步。
  3. 宿主执行前检查器校验语法与类型通过，引擎计算字面量内容哈希作为值身份。
  4. 中心主机将本次运行（`run`）、步（`step`）、值（`val`）、名字（`name`）、停止（`stop`）及事件（`run_start`、`step_formal`、`stop`、`run_end`）一次提交写入中心 store。
  5. `soroi_eval` 向主 agent 返回该步正式运行成功及运行已结束的结果。
- **涉及的组件：** `omp` 宿主、独立 soroi omp 定制包、`omp-soroi-eval`、`store`（DuckLake）。

### F02：未消费 atom 系统提醒推动 AI 逐步写出程序（被动消费流）【定】
- **一句话的用户可观察结果：** 上一步 `soroi_eval` 正式运行产出未消费 atom 后，下一轮模型请求前宿主自动注入未消费 atom 系统提醒（含 atom 名、值预览与产出它的调用），推动 AI 写下一步 `soroi_eval` 消费该 atom，多步正式运行在 store 中一步步长成完整程序。
- **从触发到结束的步骤（主路径）：**
  1. 主 agent 在第 1 步 `soroi_eval`（`formal`）中定义根 atom 或调用节点函数产出新 atom（未调用 `stop`），中心 store 提交该步。
  2. 进入下一轮模型请求前，`omp-soroi-eval` 的 `context` hook 读取当前运行在 store 中的未消费 atom，向消息上下文注入 `<system-reminder source="soroi">`，列出每个未消费 atom 的名字、值预览与来源调用。
  3. AI 看到提醒后，无需规划整份脚本，仅针对当前未消费 atom 调用第 2 步 `soroi_eval`（`formal`），将其作为参数传给下游节点函数产出新 atom。
  4. 原 atom 因被正式运行的捕获作为输入而变为“已消费”，新产出的 atom 进入下一轮提醒，直至 AI 在末端调用 `stop` 使全部末端 atom 消费完毕。
- **涉及的组件：** `omp` 宿主、`omp-soroi-eval`（`soroi_eval` 工具 + 未消费提醒 hook）、`store`。
- **依据的 `(U)` 原文：**

## 二、两阶段运行：`dry run`（含钉住昂贵调用）到 `正式运行`（F04–F05）

### F04：`dry run` 真实试跑与外部钉住（Pin）昂贵调用且零 Store 写入【定（`pins` 参数格式为【暂定】）】
- **一句话的用户可观察结果：** AI 以 `dry_run` 模式调用 `soroi_eval`（可叠加外部钉住的节点返回值以挡住昂贵设备或 `Agent` 副作用，而不改动被测代码本身），未钉住的节点真实执行，结果当场通过工具返回交给 AI，且 `store` 中从头到尾不写入任何记录。
- **从触发到结束的步骤（主路径）：**
  1. AI 调用 `soroi_eval`（`mode: "dry_run"`），代码引用当前运行已在 store 中的正式 atom 或本步新定义的根 atom，并通过外部输入叠加被钉住节点的返回值（`【暂定】`：`pins` 参数的具体键值格式）。
  2. 执行前检查器完成语法与类型检查（含校验钉住返回值的类型合法性）。
  3. 求值器执行该步：遇到被钉住的节点调用时直接采用外部叠加的返回值，不触发真实设备或昂贵 `Agent`；未钉住的节点（包括本地或 Slurm 上的算法试跑）照常真实运行。
  4. `soroi_eval` 将本步各 atom 的求值结果或报错直接作为工具调用输出返回给 AI；求值出的临时 atom 随即丢弃，**不写入 `store`**，也不能被后续其他步消费。
  5. AI 可根据返回结果修改代码或更换输入 atom，不限次数重复 `dry run`。

### F19：独立 RPC Subagent 进程启动、父子/兄弟/广播 IRC 往返与忙时 Steer / 排队【定】
- **一句话的用户可观察结果：** 通过 `omp-soroi-subagent` 启动的每个 subagent 都是独立 `omp --mode rpc` 进程，登记进主进程 `AgentRegistry`；父子、子父、兄弟间可通过 `write agent://<id>` 与 `agent://all` 发送带来源的 IRC 消息并用 `wait` 等待回复；收件方忙时父消息作为 steer 注入当前轮、同辈消息排队到步边界。

  1. 主 agent 调用 `soroi_task`（或在 `soroi_eval` 中并发调用多个 `Agent` 节点）启动子 agent `Alpha` 与 `Beta`，各自拉起独立 `omp --mode rpc` 进程。

  3. 当 `Alpha` 正在执行长任务（`running`）时，主 agent 向 `Alpha` 发送 IRC 消息，该消息带 `fromParent` 标记作为 steer 立即并入 `Alpha` 当前回合；兄弟发来的消息则进入队列。

### F20：Subagent 空闲超时停驻（Park）、唤醒死 Session、Kill（Tombstone）与复活【定】
- **一句话的用户可观察结果：** Subagent 回合结束进入 `idle` 后，超过空闲 TTL 自动进入 `parked` 并退出子进程；后续再次给它发 IRC 消息时，主侧以同一份 `.jsonl` transcript 重新启动 `omp --mode rpc` 进程唤醒它；在 Agent Hub 执行 kill 使其进入 `aborted` 并生成 `.tombstone` 文件，再次发消息时自动删除 tombstone 并复活同一份 transcript。

## 七、单步多路平铺并发与下游汇总比较（F22）

### F22：一步 `eval` 内平铺多条调用并发执行多路算法/多验证实例、来源提醒与下一步汇总比较【定】
