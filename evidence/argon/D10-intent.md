### 1. U30、U32（“先开发好再 e2e”与“合并仓库使 e2e 成本巨高”）的本意，及其与 U2、U23、U1 的统一

#### 裁决 1.1：`“先开发好再做 e2e 测试”` 的本意是恢复 U2 的阶段顺序，废除切片级/波次级中间全栈 e2e 环节 `【定】`

- **用户本意裁决：**
  1. **阶段顺序是“先完成开发实现，再做全流程 e2e 测试”（U2、U32）：** 用户在 **U2** 中明确给出了线性全流程顺序：**“从设计，到补充，到开仓，到实现，到e2e测试”**。在 **U32** 中用户直指病灶：**“引入过多的中间环节做e2e而不是把东西开发好后再做e2e测试是你一开始规划的就有问题”**。
  2. **D8 规划违背本意之处：** D8（D8-13、D8-14）把实现切成了 VS1、VS2、W1–W6 八个波次和 108 个微型切片，规定每个小切片合入都必须完成跨组件 runtime 验收、双讨论者审查、独立 review 与 rebase 重跑，并在半成品阶段插入了 VS1/F01、VS2、E2E-01～E2E-21 等大量中间全栈 e2e 门禁，导致 **“一点点小改动要验收整个soroi，而过去了几个小时根本没做多少功能，所有的ai都在互相等待”（U30）**。
  3. **与 U2（不擅自收缩）、U23（走通所有流程、作为 Pepgent agent 核心、盘点点线面）如何一起成立：**
     - **砍掉的是“开发过程中的中间 e2e 环节”，绝不是收缩最终的 e2e 验收范围。**
     - **实现阶段（先把东西开发好）：** 各组件的工程进程在各自独立仓库内并行把全部功能开发完毕。开发期间只需通过本仓库、本进程边界内的局部自测（如单服务 HTTP/DuckLake 测试、单插件协议测试、单二进制测试），**严禁要求每个开发切片拉起完整 soroi 容器栈、打包完整 release tar 或跑跨仓库 e2e**，从而彻底消除工程进程之间的跨仓等待（U30）。
     - **e2e 测试阶段（开发好后再做 e2e）：** 待各组件代码全部开发完成并合入各自仓库后，统一组装完整 `soroi` omp 定制（U23），集中执行前置验收 A0、第一段 S1（soroi 全流程 F01–F30）与第二段 S2（接上真实 Pepgent 走通业务全流程 F08–F31），并在此基础上完成 Pepgent 与 soroi 之间缺失的“点、线、面”差距盘点（F32 / D9），完整兑现 **U2** 与 **U23**。
- **`(U)` 原文依据：**
  - **(U) LEDGER U30：**
    > “我不知为何你要在最初把仓库合并成一个mono repo，导致一点点小改动要验收整个soroi，而过去了几个小时根本没做多少功能，所有的ai都在互相等待”
  - **(U) LEDGER U32：**

  - **(U) LEDGER U2：**
    > “这是一个从设计，到补充，到开仓，到实现，到e2e测试的全流程任务，不要擅自收缩，并且要随时随地用agents.md主动维护好进度，对于需要排期实现，我推荐你使用一个agent作为秘书，pepgent专门存在pm仓库和对应的github project。对于独立的实现任务，你完全可以在指挥subagent，把某个subagent视作工具去操控tern，创建完全独立的全功能omp 进程和会话，并通过各种通讯工具指挥，而不依赖完全自己的subagent，把所有的活全部都揽给你，我推荐你在正式工作流程中，调查好核心思想后，你自己的session是领导人团队，而工程师，实现者，测试，则是tern中各自其他目录的完整agent，并且他们自己可以派生自己的subagent做实现。”

#### 裁决 1.2：`“合并仓库使 e2e 成本巨高”` 的本意是废除 `Pepgent/soroi` 大一统 monorepo，按独立组件分仓自治 `【定】`

- **用户本意裁决：**
  1. **废止 D2-02/03/04/24/25 与 D6-22 的单仓合并（U30、U32）：** 用户工作区原本就是按组件分仓分目录的（`pepgent-soroi` 设计、`pepgent-omp-soroi-eval`、`pepgent-omp-soroi-subagent`、`pepgent-remote`、`pepgent`）。D2 将 `eval` 插件、`subagent` 插件、中心 `store` 服务、定制配置（`agents/`、`skills/`、`rules/`、`settings/`）与全栈 `e2e/` 合并进 `Pepgent/soroi` 单一 monorepo（并归档了两个旧插件仓、绑定同版本单一 release tar 发布），直接导致多个工程师争抢同一仓库、任何一处微调都牵动整个 soroi 的构建与验收。本人此前在 `argon/D2-rulings.md` 中同意将 `store` 与插件并入 `Pepgent/soroi` 同仓同版本交付，属于对 U23 的错误延伸，现依据 **U30、U32** 正式撤回并推翻。
  2. **与 U1（组件独立存在）、U2（tern 中各自其他目录的完整 agent）、U23（完整 omp 定制）如何一起成立：**
     - **组件独立存在与物理目录隔离（U1、U2）：** **U1** 明确规定 **“soroi本身相当于只是omp的扩展组件，离真正的pepgent还很远，对于pepgent下的组件归属，就像remote一样他本质上不属于soroi是独立存在”**；**U2** 明确规定 **“工程师，实现者，测试，则是tern中各自其他目录的完整agent”**。各组件（中心 `store` 服务、`omp-soroi-eval` 插件、`omp-soroi-subagent` 插件、`remote`、`omp-rpc-mux`、`lab-library`、`images`、`deploy`、`Pepgent`）在各自的独立仓库与独立目录中开发和自测，互不阻塞。
     - **“完整 omp 定制”（U23）是最终交付与安装契约，而非源码 monorepo：** **U23** 要求“一定是一个完整的omp定制”，指的是最终交付给干净 `omp` 宿主安装运行的产物包含完整的插件、设置、agent 定义、技能与规则，能够与中心伴随服务（`store`、`omp-rpc-mux`）及 `remote` 协同走通全部流程并作为 `Pepgent` 的 agent 核心。源码按组件拆分为独立仓库开发，在最终进入 e2e 阶段时通过发行/安装清单组装进干净 `omp` 容器，使 **U1、U2、U23、U30、U32** 完全自洽。
- **`(U)` 原文依据：**
  - **(U) LEDGER U1：**
    > “对于soroi的的业务，在pepgent/pepgent目录，并且已有agent在制作纯前端，目前soroi的设计对于完整的pepgent是不够的，另外，soroi本身相当于只是omp的扩展组件，离真正的pepgent还很远，对于pepgent下的组件归属，就像remote一样他本质上不属于soroi是独立存在，后续对于缺失的组件，形态，功能，如何规划，必须由你和argon共同考虑好”
  - **(U) LEDGER U2：**

### 2. U38、U39、U11、U12、U21 对领导层权力归属的要求与边界划分

#### 裁决 2.1：“leader 单独裁决”与“工程师自决”各自哪里违背用户本意 `【定】`

1. **“leader 单独裁决”（LEDGER E28）违背 U38、U11、U12、U14、U20、U21：**
   - **违背事实：** 实现期间，leader 以“技术澄清（leader 裁决，不重投）”名义，未经 argon 意图审查、未经导师与 `task:high` 审议、未在 `Pepgent/PM` 建表逐条投票，单方面通过 `peer_send` 和评论对二十多项跨组件契约、设计补充及范围取舍直接拍板（如 REM-07 终态语义、LAB-04/10 角色权限矩阵与 D9 候选豁免、SOR-08 提醒注入位置、STO-05 游标契约、SOR-06 加载器限制等），并把所有工程通讯汇集到主会话亲自包办。
   - **违背的本意：**
     - 违背 **U38（“你这死妈废物就这么喜欢把权力拿在自己手里，你也配？”）**：用户严禁 leader 个人独占决策权。
     - 违背 **U11、U12、U14、U20**：所有设计和重要决策必须由领导小组（leader、leader 分身、`task:high`、argon、导师）共同参与（U11），在 `Pepgent/PM` issue 中按表格条目（写明 `what`、`where`、`how`、取舍）进行三模型族民主投票（U12、U14、U20），对缺失部分与设计补充须经 argon 一票否决权审查（U11）。
     - 违背 **U21（“对于领导的处理，我推荐你分身，而不是自己处理，你应该专注于推进”）** 与 **U20 第 5 条（异步总线）**：治理与决策流程应交由 leader 分身与秘书（U2、U14）协同处理，leader 主会话应专注推进而非集权包揽。
2. **“工程师自决”（LEDGER R63、E29）违背 U39、U11、U12、U26：**
   - **违背事实：** 在 U30 批评等待过长后，leader 向全部工程进程广播“实现层取舍由工程师自决并写进 issue；只有已投票的跨仓接口改动才上报，上报期间不停工”。
   - **违背的本意：**
     - 违背 **U39（“你这死妈畜生拿劣质借口妄想取消领导层？”）**：借“减少等待”之名，把本属领导小组的设计补充与重要取舍下放给实现工程师，实质上架空并取消了领导层（U9、U11）。
     - 违背 **U11（“所有的设计，和重要决策，不允许使用task high以下的模型参与，只能是你，你的分身，task high，argon，导师”）**：实现工程师及其派生的 `task:mid` / `task:low` / `task:free` 严禁越权做设计或重要取舍。
     - 违背 **U26（“在任务足够清晰，设计足够可靠，决策项足够小，任务不是很庞大的时候，task low和task free都十分可靠”）**：低成本实现模型可靠的前提是**领导层先把设计定可靠、把决策项切小**，而不是把未决决策甩给工程师自决。

#### 裁决 2.2：哪些事项必须回领导小组、哪些实现细节可交工程师 `【定（边界原则） / 暂定（具体操作细则）】`

- **必须回领导小组（严禁工程师自决，严禁 leader 单人拍板）的四类事项 `【定】`（依据 U1、U11、U12、U14、U23、U24、U38、U39）：**
  1. **用户意图、功能范围与 D9 缺口归类（U1、U2、U23）：** 任何关于某项功能“本版做不做”“算不算 MVP 流程”“是否留作 D9 点线面差距候选”的判断，必须经 argon 凭 `(U)` 原文裁决并经领导小组表决。
  2. **缺失部分与设计补充、跨模块串联方案（U1、U11）：** 凡 `design/*.md` 或已表决决策表（D1–D8）未规定、在实现中暴露出的设计空白（如宿主 hook 介入点、生命周期异常终态、派生运行事务规则等），一律归领导小组（含讨论者、argon、导师）协商并按条目投票，argon 对缺失部分与设计补充享有否决权（U11）。
  3. **跨组件 / 跨仓库契约与权威状态模型（U11、U12、U14）：** 任何涉及两个及以上组件/仓库的 HTTP/SSE/WS/RPC 接口、wire JSON Schema、Parquet 批次列、DuckLake/业务库表结构、角色权限矩阵、状态权威源头与生命周期起止锚点的变更或增补，必须回领导小组走 PM issue 逐条投票。
  4. **soroi 独立 omp 定制的提示词与规则设计（U11、U23、U24）：** agent 定义、skill、rule 的设计内容属于核心定制设计，必须由 `task:high` 或以上模型参与并经领导小组与 argon 审查（U11）。
- **可交由工程师在各自仓库内决定的纯实现细节 `【定（原则依据 U2、U13、U26） / 暂定（具体清单供 D10 表决）】`：**
  - **前提（U26）：** 领导小组已将设计定稿、接口契约与错误/状态类型完全锁定，任务足够清晰、决策项足够小。
  - **允许范围：**
    1. **单仓库、单模块内部的私有代码结构：** 不改变对外 API/CLI/RPC/HTTP schema、不改变状态生命周期与持久化格式的内部函数拆分、文件组织、私有辅助类型与算法实现；
    2. **已选定开源库的标准调用实现（U13）：** 在领导小组已表决选定开源方案且不修改 `omp` 宿主代码（U13）的前提下，按库文档编写具体调用代码；
    3. **本仓库局部验证脚本编写：** 为验证本仓功能编写的仓内测试与局部运行验证脚本。
  - **阻塞上报铁律：** 工程师一旦发现契约未定义、跨组件字段不匹配或设计空白，必须在异步总线（issue 评论）标记 `BLOCKED` 上报领导小组，**严禁自行扩充契约或猜写设计（U11、U39）**。
