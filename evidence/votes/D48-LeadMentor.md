## 正常主路径（不涉及失败或竞态）

首次注册后，Pepgent/images上有只读deploy key A，本地owner文件保存A的私钥，部署使用A。随后按本行how“轮换”明确沿用D47-01 v2的顺序：

1. 生成新密钥对B；
2. 向同一images仓库注册新的只读deploy key B；
3. 覆盖同一owner文件、走variables/preview/apply，让lab-web挂入B；
4. 最后删除旧deploy key A。

在第2步到第4步之间，GitHub持有两个不同key id的实体A和B。这是正文要求的正常有序轮换，不是并发、异常、重试或恢复场景。

## 精确契约冲突

D48-01 v1 how“护栏”同时要求：

- 开关打开后，org内“只存在这一把deploy key”；
- “新增任何其他deploy key都要另行立案”。

B不是A原地修改后的同一GitHub对象，而是POST新创建的另一个key。故执行轮换第2步即违反单把实体护栏；若为维持单把而先删A，则违反本行沿用的“最后删除旧key”的明确顺序。若强行每次轮换再立案，又给已授权的正常凭据生命周期增设了原本不需要的议会前置。

可定位源头：当前D48-01 v1正式表的how“护栏”“轮换”两段；D47-01 v2正式表how“轮换”段明确写“生成新密钥对，注册新deploy key，覆盖同一owner文件……最后删除旧deploy key”。GitHub注册接口是POST /repos/Pepgent/images/keys，返回新id，本行登记也以id辨识对象。
