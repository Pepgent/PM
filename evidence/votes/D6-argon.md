    2. **(U)** `session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/543f0ccd`（2026-10-31 05:29:58）：

### 2. `D6-14`（分类：意图 + 串联 | 设计补充 I-1、I-2）：改值——中止在途捕获，由 `Human` 交回替代并通知 AI
- **意图面裁决：`【定 · 符合用户原意，无冲突】`**
  - **依据 `(U)` 原文：**
    1. **(U)** `session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/ba5ad307`（2026-10-31 05:16:25）：
       > “不，写方不一定只有ai，可以是人在gui写，写了以后通知ai改变了，但是值已经进去了”
    2. **(U)** `session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/d1baf561`（2026-10-31 05:18:56）：
       > “我觉得合并写入是不对的，人类写这种操作等于，将一个运行的程序取消，原本的atom要经过程序消费，现在经过一个特殊的程序，就叫他人类接入，所以产生了新的atom，然后自动触发函数消费”
  - **裁决说明：**
    - **【定】** 人在 GUI 改值绝不是多写方合并覆写 store，而是取消正在运行的程序、改由“人类接入”（`Human` 捕获）产出新 atom、自动触发同一步已写好的下游函数消费，并在步提交后通过 eval 返回结果与未消费提醒通知 AI 值已被人类介入改变。
    - **【暂定】** 将“改值（`Human` 替代产出）”限定在在途调用、已提交调用走 `D6-16` 派生运行，以及 `Human{replaced}` 的具体字段结构，属串联与技术设计补充，与 `(U)` 原意一致。

### 3. `D6-16`（分类：意图 + 串联 | 设计补充 S-2、I-2）：派生运行——改参数或函数体，只自动运行被改的那一个调用，下游不按已存步重放
- **意图面裁决：`【定 · 符合用户原意，无冲突】`**
  - **依据 `(U)` 原文：**
    1. **(U)** `session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/ba5ad307`（2026-10-31 05:16:25）：
       > “原本是soroi就有暂停运行然后改了重跑，等于是仅更改输入值后跑同样的preset，这对于现在来说是一样的，新的实例，新的参数，旧的函数体，所以要写的东西比你想的要多”
    2. **(U)** `session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/a0d22b8a`（2026-10-31 08:32:02）：
       > “eval因为明确存在正式运行，正式运行同等于固化，所以才有人类介入的可能性，人类修改正在运行的函数体并派生新的闭包这件事永远都是正式运行”
    3. **(U)** `session://01a18efe-a680-7642-aff1-6f468cf2935e/entry/9e2d37a1`（2026-10-31 07:58:00）：
       > “没有重放，这是意淫的东西”
    4. **(U)** `session://01a18e8a-ba9d-76af-acd2-8e12765ec3e4/entry/21495b13`（2026-10-31 08:47:13）：
       > “跑你妈同一份脚本，从来就没有重放”
    5. **(U)** `session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/63f31453`（2026-10-31 08:18:31）：
       > “跨会话消费从头到尾就是错的，听不懂？难道要开好几个atom互相看见atom？那我拆你妈库呢”
  - **裁决说明：**
    - **【定】** 派生运行 R' 永远是正式运行；上游未受影响部分按身份继承到 R' 自己的名字空间（不跨运行直接消费父运行 atom），被修改的调用 C 作为 R' 的第一步自动运行（“新的实例，新的参数，旧的函数体”或新版本函数体），而 C 的下游由 AI 根据未消费提醒继续逐步写出，绝不按父运行已存的旧步自动重放（replay）整份脚本。

### 4. `D6-22` 及 `D6-01`（分类：意图 + 串联 | 补充 U23、U24）：store 服务在 `Pepgent/soroi` 独立 omp 定制中的归属、打包、安装与被 Pepgent 调用
- **意图面裁决：`【定 · 符合 U23 与 U24，无冲突】`**
  - **依据 `(U)` 原文：**
    1. **(U) LEDGER U23**：
       > “对于soroi的最小功能合集，一定是一个完整的omp定制，并且能走通我说的所有流程，并且能作为pepgent的agent核心，并且最后能在这个基础上知道pepgent和soroi之间缺失的点，线，面”
    2. **(U) LEDGER U24**：
       > “不要混淆soroi和omomp，soroi并不是完全基于omomp的，他提出的fork在soroi根本不应该存在，soroi是独立的omp定制”
    3. **(U)** `session://01a18dd4-e638-75ad-a5f3-f0537daf3896/entry/2d861491`（2026-10-31 02:33:44）：
       > “所谓的捕获和记录，本质上只是omp里所需要的自定义插件罢了”
    4. **(U)** `session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/64246eaf`（2026-10-31 05:07:53）：
       > “通常来说，以omp的视角来看，store天生是session log，但是，如果store不是session log，而是能落盘的状态管理，则直接解决后期复用，值怎么存储，捕获，前端连dsl都不要了”
    5. **(U)** `session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/8e0a7e8f`（2026-10-31 05:35:38）：
       > “对于运行中的数据，实际上他们各自是独立的db，而只有运行结束后，才会随着拷贝一起回集中副本，根本没有并发不并发写入的问题，而写入这事，本来就应该本机落盘，而不是，有一堆集群，维护一个中央的数据库全写一个库”
  - **裁决说明：**
    - **【定】** store 属于 soroi 引擎自身的值权威（不同于用户显式划出 soroi 的 `Pepgent/remote` 与独立网络层 `Pepgent/omp-rpc-mux`），收回 `Pepgent/soroi` 单仓的 `packages/store` 与 `packages/omp-soroi` 同仓同版本交付，并由同仓 compose 拉起伴随服务，使 `Pepgent/soroi` 作为独立的完整 omp 定制（不含任何 omomp `fork` 机制）能脱离 Pepgent 走通全部流程，同时能通过 `SOROI_STORE_URL` 作为 Pepgent 的 agent 核心被 Lab 后端调用。
    - **【暂定】** 单写方以独立 Bun 常驻进程承载 HTTP 接口的具体进程拓扑（源自 `(A)` `01a18e1f #99c65d16` 经 `(U) #bfd6975c` 拍板写文档，无冲突的 `(U)` 原话）。
