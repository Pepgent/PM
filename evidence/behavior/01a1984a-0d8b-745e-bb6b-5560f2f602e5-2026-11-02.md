## 四、角色/制度改进建议（限派工粒度、边界与低阶 watchdog）

1. **W-10 派工模板增加一次性结构校验：** 每个 task item 必须只有一个主题；写文件必须显式 `isolated: true` 或给出不重叠的绝对路径 allowlist；只读项才用 `isolated: false`；长报告只给 PM/local 文件路径，不在 task/context 中限字数。该校验应在调用 task 前完成，不新增人工审批。
2. **W-10 worktree 边界前置化：** 派工 brief 同时写 home 绝对路径与切片 worktree 绝对路径，所有 write/edit/bash 的 cwd/path 必须命中切片路径。临时 `WATCHDOG-LowTierScope` 可只监控：home 写入、`ask` 调用、`test*`/`vitest` 调用、真实 runtime 启动、hash 工具/字符串；命中即提醒切回合法路径或在原 issue 记录 BLOCKED，不替 agent 做设计。
3. **把 runtime verifier 从普通 W-10 implementation 闭环中拆出：** W-10 可继续写“待阶段 C 验收”的证据缺口，但不得自行把真实 browser/store/Mux 运行安排成开发期 PR 前置。若产品全景部门需要异步接缝金丝雀，由其独立派工并拥有该验证生命周期。
4. **`ALL_DONE` 采用双层状态名：** 角色定义应区分“本轮开发 PR 全部合入”和“当前阶段承载全部完成”。后者只能在所有由管理层送达的 issue/文档/E2E 编写义务均有源头记录后登记；这样不会因一轮 todo 只列六个 issue 就覆盖后续同席位义务。
5. **低阶 watchdog 只做工具边界提示：** 推荐临时 `WATCHDOG-LowTierScope`，规则仅包括：禁止向用户 `ask`；禁止 hash 生成/验证；禁止代码未完成时写/跑测试；禁止 home 写入；禁止 W-10 自行启动跨组件 runtime。它不判断产品取舍、不改变 issue 范围、不替代片区经理或治理承接者。

## 五、未观察到违例与限制

- 本报告只分析根流 JSONL；子代理的实现、测试和 runtime 动作没有在根流中逐项归因。根流对 child 的 `task`/`write agent://` 指令本身可以归因。
- 未观察到根流解密 SOPS、输出 secret、直接修改 server/protocol 生产代码、或向片区经理常规 peer_send 的确切证据。
- 未将 `wait` 次数本身判为浪费。虽然窗口内有许多连续 `wait`，但 `omomp-efficiency` 明确指出 idle/durMs 不能单独证明浪费；本报告只把有明确错误结果、并发 lock、错误工具协议或可定位返工的行为列为低效。
- 未使用 hash 值、提交 hash 对比或 GitHub 状态作为本报告的正确性证明；hash 相关内容只作为“根流调用了被禁止的 hash 工具/记录”的直接行为证据。

**最终判定：** W-10 根流在交付推进上有实质产出，但在 worktree 边界、开发期 runtime、测试时序、hash 禁令、用户提问和派工一次写全方面存在有原始 entry 支撑的偏离；其中前五项应由角色边界和低阶 watchdog 立即收口。
