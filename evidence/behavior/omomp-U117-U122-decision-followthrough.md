# U117–U122：决议落实断链的独立提效研究

## 结论与边界

OmompOptimizer-2 依 U89/U90/U94 对此次流程缺陷独立受理。用户已确认的失职、Pepgent 自身组件的 org 归属无需另行决定（U121）、管理层通知不得绕过（U120/U122），不是本报告要重新表决的问题。本部门不选择迁仓方案、不代建组件仓、不接管 Main 的迁仓 P0，不修改 AGENTS 或角色/skill 使新方法先行生效。

拟提交 P3 的新增方法只有一个：**将有后续动作的决议接续到真实执行 issue，以具名协调责任、实际承载和下一步动作保持落实生命周期；延期与待裁决不得导致事项从工作队列消失。** 通知和既有表决边界按用户要求直接遵守，不再以新方针为由重新审批已授权动作。

### 2. “非阻塞”被错误等同于“无需承载”

本部门直接读取 `local://decisions/deploy26-blocked2.md:43-46`：标题写“交 Main（不在本单范围，不发 issue）”，正文把工作树规则调和列为“只有用户能调和”的未决项，退役时仅保留为用户未决残留。盘点 F03/F04 将清理动作与规则处理区分为两个动作；本报告不决定应修改哪条工具规则，也不授权任何 worktree 清理。

这里的通用断点是：不阻塞工人其他工作，本来只说明依赖关系，却被当成不建立落实对象的理由。两者不是同一状态。保留一条真实 OPEN 跟进项不妨碍其余工程继续，也不需要建立新台账。

## 三、外部实践与现成内部原语

### 外部参考

1. AWS ADR process：https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html 。其将接受后的决策记录与执行过程区分，强调 owner 和对 action points 分配 assignee。本项目不引入另一份 ADR/决策台账，也不搬用其同步会议流程。
2. GitLab DRI：https://handbook.gitlab.com/handbook/people-group/directly-responsible-individuals/ 。仅采用“具体执行责任可以委派，但落实责任不因委派消失”的原则。**不引入其 DRI 单方最终决定权，不替代本项目的民主表决、Argon/治理否决或独立部门边界。**

### 已存在的能力

- council README 已明确：有后续工程动作的已通过行，可以 `council dispatch <行> --repo <仓> --worker <W-id> --cwd <实际home>`，按现成接口生成真实 issue、登记工人并送达。
- `pepgent-council/src/bus.ts:233-279` 的 dispatch 检查议程已定案/归档、行已通过，然后调用 createIssue、register、deliver；返回真实 issue URL 和送达回执。**它不是决策定案后自动执行**，需要有责任人实际调用，不能把存在该命令当作动作已发生。
- 管理层事务没有工程工人时，使用既有 GitHub issue 和当前记录角色职责承载，不为记录责任而假登记工人；新承载不是执行未获授权动作的许可。
- `src/council.ts:490-500` 的普通 status note 只进 Main 的 digest。它**不等于全体管理层已被通知**。投票行结果用已配置 notify/订阅；其他按当前管理层定向通知职责送达实际在席实例，传来源与承载链接，不新增人工收票通道。
- issue 是执行状态的拥有方；决议 issue/council 保持表决事实；通知/链接只是索引，不另建 local 或 LEDGER 状态面板。已发决策和调查报告不回写历史。

## 四、拟投票的明确方法

**适用对象：** 已有决议/处理结果中仍有后续动作的事项，包括延期、待裁决、退役残留，以及“之后另行派发”的工作。不是要求每个纯说明性决策建一个空 issue，也不是每个工程小切片单独开验收仪式。

### Before

`决议关闭 → how 写“以后另派/等用户” → 无执行 issue、无具名落实者 → 下次汇报再向用户重复提出同一问题。`

### After

`决议/处理结果 → 既有 how 写清落实协调席、真实承载（或由谁在哪个现有仓创建）、下一动作 → 按既有管理层职责通知来源和承载 → 已授权动作由有权限者执行，实际 issue 保持 OPEN 至对应执行义务完成。`

具体做法：

1. 起草有后续动作的行时，在已有 how 中写清**落实协调席、执行承载、下一动作**。协调席是继续推进并接起执行者的现有管理职能，不是让独立部门接日常杂务，也不是要求某个一次性 desk 永久常驻。
2. 落实协调席收到通过/处置结果后，沿用真实存在的执行 issue；没有时，在既有合适仓创建落实 issue 并登记具名责任人与下一动作。目标组件仓尚不存在时，也不能把候选仓 URL 当真实承载；在已经存在的合适管理/来源仓保留此义务。
3. 工程派发在议程满足 dispatch 条件、已有实际工程席时使用原生 council dispatch/deliver；管理记录工作按现有秘书或一次性 desk 职责办，不编造 worker。一次性实例结束时，把真实 issue 和已发生的下一步交回持续负责的协调席，而不是把“给过 brief/投递成功”写成已执行。
4. 暂不能执行的工作仍在同一真实 issue 保留具名协调责任、具体未定事项、已完成的可达部分和下一管理动作；不以“等用户”“非阻塞”“不在本单完成范围”为由删去落实义务。按当前 U 原话及已有权限判断下一步，不由执行者新造管理层/用户分类白名单；Pepgent 自身组件 org 已由 U121 纠正，不再重新表决。
5. 用户要求的管理层通知照常执行，已授权动作通知后连续推进，不新增“等全席回复”的锁；需要新表决的仍按现行队列和资格席办理。不能用补通知或登记 issue 洗白未获授权的变更。
6. 投票归档与执行结案分开。只有对应执行义务的拥有方给出事实证据，才关闭该执行项；不以决议关闭、建了仓、发了消息或写了草稿替代迁仓完成。不存在新的全局扫表、人工核账或同步验收步骤。

**拟落点（通过后才改）：** 一个 project skill `decision-execution-handoff`；`decision-vote` 与 `governance-desk` 仅引用该方法，不各写一份副本。不改 council 程序或 schema，不私改 AGENTS 受理范围，不改变现有通知/表决权限。

## 五、量化收益与验收

- 已证明的样本代价：用户确认至少 8 次重复推回；2 个迁仓义务当时无执行 issue；独立盘点另给出 2 个无独立完整承载的未决动作；一次未经程序的规则更正导致至少 2 个补救写调用和 42.313 秒经过时间。不能将整个迁仓延期时长或所有 wait 都计为浪费。
- 条件性收益：对那 2 个迁仓义务采用同一真实 issue 和具名协调责任后，至少不再需要靠下一次用户追问重新发现它们；盘点中的 4 个动作都有可追踪入口。8 次重复推回是应消除的行为样本，不声称已实测减少到零，也不把预期收益冒充 runtime。
- 通过后真实验收：一个新派 governance-desk 实际加载 skill，拿一条真实已通过且尚有执行动作的行，复用/创建真实跟进 issue，核对来源、协调责任和下一动作，并实际使用适合该事项的既有通知/派发路径。观察最终 issue 与送达结果；检查仍未完成的执行项没有因决策归档而被误关。不创建假工人、测试决议、假 issue 或 mock 来冒充业务路径。
- 本提案不会等待迁仓 P0 才做研究，也不会把本提案表决/验收设为迁仓执行的前置门禁。正式方针按 U90 走 P3；用户已直接确定的事项不重投。
