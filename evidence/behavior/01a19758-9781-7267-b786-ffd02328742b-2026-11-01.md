## 5. 制度与角色定义改进建议

以下建议只涉及派工粒度、角色边界与低阶监督，不涉及产品范围或 e2e 判据设计：

1. **W-08 派工模板固定写明“本轮不调用 `discuss:*`”。**
   已通过契约内的实现由工人连续完成；遇到公开契约、路径授权或验收语义空白时，在原 issue/PR 写 `BLOCKED`，由片区经理送达治理路径。不要把 medium 讨论任务当成事后批准或开工锁。

2. **显式声明根 lockfile 是否属于授权路径。**
   默认白名单仍为 `e2e/**`、`compose.yaml`、`compose.full.yaml`；若某切片新增 e2e 依赖确实必须更新根 `bun.lock`，派工时把 `bun.lock` 单独列为允许路径，并在提交前核对 staging 路径。这样不需要工程师猜测“依赖联动是否自动授权”。

3. **把禁止的来源/工具边界写成 W-08 专属高信号规则。**
   明确：不读 `history://` / `session://`；PM 文件只走约定的 GitHub file read/`gh api`；文件读搜改使用 native 工具；shell 只执行经契约允许的编译、类型检查、Git 和状态写入命令。不要增加每条命令前审批。

4. **临时开启只告警的 `WATCHDOG-LowTierScope`，限定 W-08 一个窗口。**
   仅检测并记录 entry/timestamp：
   - `history://` / `session://` 读取；
   - `discuss:*` 派发；
   - `local-smoke`/测试命令后仍出现代码编辑；
   - `git add` 命中白名单外路径；
   - shell `grep`/`sed` 读搜改。
   看门狗只报警，不把报警变成逐命令审批锁、每 PR 盖章或跨组件 runtime 门禁。连续一个新窗口无告警后撤销。

5. **把“作者完成后再检查”写成一次性顺序条件。**
   `check`/类型检查仍可保留为阶段 B 的本仓检查；但 `local-smoke` 等测试/oracle 只能在该切片代码写入完成后运行。不要把这个顺序扩展成每个文件或每个子任务都单独验收。
