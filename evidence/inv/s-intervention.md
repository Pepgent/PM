## Decisions

### D1. 人可以在 GUI 改正在运行的业务；不只是 AI 写入

**(U)** S1 **#ba5ad307，05:16:25**：

> 不，写方不一定只有ai，可以是人在gui写，写了以后通知ai改变了，但是值已经进去了，这个写是这样的，原本是soroi就有暂停运行然后改了重跑，等于是仅更改输入值后跑同样的preset，这对于现在来说是一样的，新的实例，新的参数，旧的函数体，所以要写的东西比你想的要多

来源：[S1/#ba5ad307](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/ba5ad307)。

明确决定：GUI 人类也是修改发起者；更改应产生新实例/新参数，不覆盖旧函数体；AI 应知道发生了人类修改。**“直接往 store 合并写值”不是这段话的最终落法，随后被 D2 修正。**

### D2. 人类改值是替换一次消费：取消程序 → 人类接入 → 新 atom → 继续消费

**(U)** S1 **#d1baf561，05:18:56**：

> 我觉得合并写入是不对的，人类写这种操作等于，将一个运行的程序取消，原本的atom要经过程序消费，现在经过一个特殊的程序，就叫他人类接入，所以产生了新的atom，然后自动触发函数消费

来源：[S1/#d1baf561](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/d1baf561)。

这是本主题最关键的纠正：人不是另一条可任意改 store 值的写入路径；原 atom 原本应被程序消费，取消该程序后，改由特殊的“人类接入”消费，并产出新 atom。**保留输入—消费—产出的事实链**，不是直接把一个旧值改成另一个值。

**(A)** 紧接着 **#7853b538，05:19:16** 将上述用户语义具体命名为 `Human` 体/捕获，并解释两种形状：

1. 人产出新参数，新实例用旧函数体运行；
2. 人直接交回原程序本该产出的结果，下游消费它。

其中原话为：“`Human`：人在 GUI 里交回结果，和交回工具是同一个形状”；“取消一个正在运行的捕获，在原来的位置插入一个人类接入捕获”。来源：[S1/#7853b538](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/7853b538)。这些是与 D2 相容的 assistant 解释，但 **`Human` 名称、与交回工具完全同形、两种插入位置**没有找到同等细度的独立 U 确认。

### D3. 人可改正在运行的函数体并派生新闭包；这永远是正式运行

**(U)** S1 **#a0d22b8a，08:32:02**：

> eval因为明确存在正式运行，正式运行同等于固化，所以才有人类介入的可能性，人类修改正在运行的函数体并派生新的闭包这件事永远都是正式运行

来源：[S1/#a0d22b8a](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/a0d22b8a)。

这不仅是“换参数”；**函数体也可改**。可介入的前提是正式运行固化；人类改函数体产生的派生闭包不进入 dry run 路径。

**(U)** 相邻的正式/非正式边界，S1 **#7ffcea0c，08:30:15**：

> eval里所有的正式远程运行才需要进入store，任何非正式运行从头到尾都不进store，否则为什么叫非正式？

来源：[S1/#7ffcea0c](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/7ffcea0c)。

**(A)** **#d8b64c7b，08:32:37** 将 D3 写成“只有正式运行才能被人类介入”“测试和试探不能被介入”“改函数体或参数派生的运行一律正式”。来源：[S1/#d8b64c7b](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/d8b64c7b)。其中“人类介入仅正式运行”的总体边界有 U 依据；把它扩展到 **所有普通 IRC 对话是否也受同一限制**，用户原话未单独说明，见 Open questions。

### D4. 接管 subagent 用现有 IRC 输入语义；可辨来源，可排队、可被人编辑

**(U)** S1 **#7bfe3696，04:42:56**：

> 而实际上做人工接管也是可以的，因为omp的subagent语义里一切都是irc，所以irc可以知道来源是主agent，而irc可以是一条普通的user prompt，所以可以派对，乃至被人类编辑

来源：[S1/#7bfe3696](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/7bfe3696)。

注意原文是“**派对**”，本报告保留原字，不伪造为“排队”。**(A)** 随后的 **#c7ab2296，04:43:14** 将其解释为同一 IRC 输入路径、人的来源标记、可插队、可撤回未投递消息/编辑后重发，并引用当时 RPC 队列能力。来源：[S1/#c7ab2296](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/c7ab2296)。

用户直接建立的是 **IRC / 来源 / 普通 user prompt / 人类编辑** 的方向；**“人的来源标记”的具体结构、插队、撤回—重发的操作细则是 A 的展开**。当前文档采用了其中一部分，不等于已取得逐条 U 确认。

### 2. 明确遗漏的用户效果：人改了，AI 应知道

**(U)** #ba5ad307 明确说“写了以后通知ai改变了”。**(D)** intervention.md:11-17 只写 Human 新值和“下游自动消费”，没有写 AI 能看到这是人改的、改了什么。**(A)** #28a84181 曾把通知解释为未消费警告，#7853b538 又解释为已绑定下游直接消费、不需另通知；它们不是同一个主路径说明。

**缺口性质：** 用户效果遗漏/与消费路径未接合。不能因此擅自增加一套通知总线；现有 **(D)** eval.md:160 已要求未消费提醒带名字/预览/来源，但还没有明确 Human/派生运行如何进入这条路径。

### 3. “自动消费”的接续对象不清楚，不能恢复成旧的预编排 workflow

**(A)** #7853b538 当时解释：“下游消费者在 bind 链里本来就定义好了，新 atom 一出现，按消费规则就会被消费”。**(D)** 当前 eval.md:5 则写程序不是一次写出来，AI 每次根据未消费 atom 写下一步；:119-122 写未消费 atom 是待办、没有调度器决定下一步。

**(D)** intervention.md:15 的“下游按消费规则自动消费”没有说明此处是：已有捕获/函数自动重求值，还是产生未消费 atom 交回 AI 写下一步。**(U)** #d1baf561 要求自动触发消费，但没单独决定这个更细的接续界面。

**缺口性质：** 新旧讨论阶段的接口没有收束；不是已证明的用户矛盾，也不是允许重新引入 preset/独立调度器。

### 4. Human 替换输出与“改参数后重跑”的主路径没有区分

**(U)** #ba5ad307 明确想要新参数/旧函数体的新实例；**(A)** #7853b538 给出了“改参数后重新跑 P”和“人直接交回 P 的结果”两种位置。**(D)** intervention.md:9-17 的“改值”没有说明 GUI 本次提交的是输入参数还是替代输出；:19-25 又把“改参数”放进派生运行一节。

**缺口性质：** 两条本来都在讨论中的主路径边界不清；Human 捕获与派生运行是替代选择、还是一次介入可同时产生两者，尚未交代。当前 :33 的“或”不能自动回答。

### 5. 中止捕获写了意图，没交代实际执行层的主路径

**(D)** intervention.md:13 只写“中止正在运行的那次捕获”；layers.md:14 要求中止后远程执行随之结束；subagent.md:18 对标生命周期，:43 区分中止当前一轮与 kill agent（该行是文档中的验证汇报，非本次 R）。

**缺口性质：** 读者不知道介入时取消的是捕获、一次 agent turn、整个 agent，还是 remote 执行，也不知道由哪个已有入口执行取消。这里缺的是正常介入路径的作用对象/调用关系，不是超时、竞态、重试设计。未查实现，不能宣称这些能力不存在。

### 6. 派生闭包/运行只有结果规则，没有可执行的固化与派生操作说明

**(U)** #a0d22b8a 的用语是“函数体”“新的闭包”。**(D)** intervention.md:21-25 写成“新的运行”，仅规定正式、父运行、复用/重跑、不改旧记录；eval.md:76 与 store.md:30 定义文件即函数版本；store.md:18 的运行记录只有父运行与“改了哪些输入”。

**缺口性质：** 用户要求的函数体编辑如何成为新闭包/新函数文件版本、派生运行从哪个固化程序取得其余部分、如何重新带入已有输入，正文没有把这条主路径连接起来。捕获记录已有节点函数版本（store.md:16），因此不能误报“完全没有版本记录”；真正欠缺的是 **编辑 → 派生 → 执行** 的关系说明。

### 7. Human 交回接口只有类比，缺正常输入/输出契约

**(D)** intervention.md:17 仅说与交回工具同形；eval.md:71 有 `human(request) -> Fn<'Human', …>`，:86 定义 agent 交回结果和文件路径；store.md:16 的统一捕获记录要求节点函数版本、运行环境、输入身份、产出字段和所属步。

**缺口性质：** 尚未说明 GUI 从哪里收到本次 Human 请求、如何展示原输入、提交怎样的字段/文件、这条捕获归属哪个步/运行。函数式形状已经有，不是完全未设计；从 GUI 到正式捕获的具体契约仍只有一句类比。这里不要求新增验证、异常处理或恢复机制。

### 8. IRC 接管不是一个完整的 GUI→IRC→agent 主路径

**(U)** #7bfe3696 要求普通 prompt/IRC 语义；后续 **(U)** 插件 session #f488be08 要求生命周期/IRC 全方位对标内置。**(D)** intervention.md:29 一句话规定来源与队列编辑；subagent.md:21-22 定义主侧控制、GUI 多读方；:94-99 说明现有来源/忙闲投递依据。

**缺口性质：** 没有交代 GUI 向哪个已有写入入口提交人的 IRC、人的来源如何传到接收方、如何选择与编辑那一条未投递消息。当前文档也没有明确“接管”只是发指令/编辑队列，还是有持续的控制归属变化。不能从“接管”二字自行增设独占模式或控制权仲裁。

### 9. IRC 接管的记录与 store 的“介入只新增”关系未定义

**(D)** intervention.md:33 列出 Human 捕获或派生运行；store.md:19 却有“人类介入”事件类型，:23 规定对话归 omp transcript。**(U)** #7bfe3696 把接管视为普通 IRC prompt，并未说每条人的 IRC 都必须创建 Human 捕获/新运行。

**缺口性质：** 文档没写纯 IRC 介入是否只留 transcript，是否另记 store 介入事件，以及如何连到后续产物。不能把“发一条人的 IRC”直接等同于“人交回一个结果”。这也是 :33 对 :29 的范围没有解释清楚，而非已证明数据设计错误。

## Open questions

以下是证据尚未闭合的 **主路径问题**，不是建议设计异常/竞态处理；列问题不等于要求现在追问用户，后续应先从当前实现与其他已授权证据补足。

1. **普通 IRC 接管也必须在一个正式运行内部吗？** **(U)** S1 #a0d22b8a 限定固化运行上的函数体编辑；**(D)** intervention.md:7 是全局“只正式”，:29 又泛指接管 subagent。现有证据未明确普通非捕获 agent 对话是否也受这条限制。
2. **“自动触发函数消费”在当前逐步 eval 模型下具体是什么？** **(U)** #d1baf561 的要求明确；**(A)** #7853b538 的 bind 链解释与 **(D)** eval.md:5、:117-122 不同阶段。需要明确 Human 产出如何触发已定义函数或下一轮 AI。
3. **一次“改参数并重跑”是否同时生成 Human 捕获和派生运行？** **(U)** #ba5ad307、#d1baf561，**(A)** #7853b538，**(D)** intervention.md:9-25、:33，尚未给出统一关系。
4. **派生运行中的 atom 如何获得本运行名字，避免把旧运行的 atom 当跨运行可见对象？** **(D)** eval.md:37-41 要求运行内名字唯一、别的运行看不见 atom；store.md:14、:39 区分名字与值身份。intervention.md:24 仅说身份复用，没有说明派生时形成新名字/输入的正常过程。
5. **人在 GUI 的函数体编辑如何对应用户说的“新闭包”？** **(U)** #a0d22b8a；**(D)** eval.md:64-76 采用独立 TS 文件/文件版本。不能擅自发明另一套闭包持久化或捕获环境机制。
6. **取消捕获具体调用哪个已有执行入口、结束哪个对象？** **(U)** #d1baf561 要求取消原程序；**(D)** intervention.md:13、layers.md:14、subagent.md:18、:43 还没连接为一条介入路径。
7. **人的 IRC 来源、队列编辑与“同一写方”如何接合？** **(U)** #7bfe3696，**(D)** intervention.md:29、subagent.md:21-22。目前没有依据要求持久接管模式、另一个控制通道或锁。
8. **哪几条属于已决定的具体 UI 操作，哪几条只是 A 的展开？** 撤回未投递消息/重发、人的来源字段、GUI 交回工具同形有 **(A)** #c7ab2296、#7853b538 和 **(D)** intervention.md:17、:29 支持，但未找到同细度的 U。S1 最末 **(A)** #e5335020 还明确请求确认人工接管归 intervention.md；没有把用户沉默当作确认。
9. **Human/IRC 的最终可追溯结果在哪里观察？** **(D)** store.md:16-19、:23 和 intervention.md:33 已有记录类别，但没有本次 **(R)** 证据证明 GUI 操作、agent 收到人的输入、旧捕获结束、新捕获/新运行落盘和后续消费已经串通。此报告只证明设计来源/文档缺口，不能作为实现交付证据。

## 结论

**(U + D)** intervention.md 并非方向全错：取消原消费、Human 产出新 atom、正式运行派生、函数体也可改、IRC 同一路径、独立一层，均有明确来源且核心已落在正文（对应 S1 #d1baf561、#a0d22b8a、#7bfe3696、#6145f170 与 intervention.md:3-33）。

**(U + A + D)** 半成品主要在主路径的接缝：**AI 如何得知人改了、Human 的请求/交回契约、参数修改与替代输出的区别、Human 与派生运行的关系、取消如何落实到实际执行、当前逐步 eval 的继续消费、GUI 如何经同一 IRC 写入及留下记录**。不应以新增异常机制、锁或独立调度器填补这些未交代关系；也不应把 assistant 当时提出的 bind 链/队列细节直接宣称为用户最终决策。
