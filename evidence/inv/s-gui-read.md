# GUI 读取 soroi 运行：用户意图与当前文档核对

## 范围与证据约定

本报告仅调查 2026-10-30..2026-11-01 的会话中，GUI 如何读取运行图、动态进展、草稿、运行对比和自动化可见运行事件；核对当前 `design/layers.md` 的“记录 / GUI 读取 / 运行事件”和 `design/store.md` 的“读取、订阅与检索”，必要时交叉读取同文件的数据模型、时间轴和远程数据生命周期，以及 `design/eval.md`。没有修改仓库、运行测试、读取 git 或 GitHub 历史。

- **(U)** 用户本人原话：意图事实；排除标为 agent-attributed 的提示和自动附加上下文。
- **(A)** 助手/agent 的提议、总结或本报告分析：解释，不单独提升为用户决定。
- **(D)** 当前工作树文档：说明现有文字，不证明已经实现。
- **(R)** 本次实际命令/runtime 观察；本报告没有此类行为证据。历史助手声称的验证仍标 (A)，不冒充本次 (R)。
- 本报告的差距判断标 **(A, [INFERENCE])**，并同时列出推断所依据的 (U)/(D) 证据。不是新架构或接口设计。

## Decisions

### D1. 图是运行事实的可读视图，不再用预先声明的 workflow/preset 当执行权威

**(U)** 用户最初提出的 GUI 保留方式：

> 我认为，新设计可以改变一些东西，比如eval里的特定运行，会产生记录可以另外输出某种dsl，所以gui可以渲染，而本来，运行时的workflow就不可改变，所以这一点是不影响的，然后节点库实际上没有太大存在的必要了，不一定要去掉，因为这等于可以预定义一些东西持久化，下一次eval进来直接import后传参

证据：[H #47b71e05，2026-10-31 04:02:49](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/47b71e05)。这里的 DSL 是当时的输出设想，不是最终要求，后被 D2 简化。

**(U)** 业务保留的总方向：

> 大体上来说，我认为虽说动了核心设计，但是app层的业务好像几乎不用动，只是因为反转以后，体验更好了

证据：[H #e3692177，04:03:59](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/e3692177)。这是总体判断，不能据此把原型的每个交互细节都提升为系统硬约束。

**(A)** 当时助手解释：GUI 需要“谁消费了谁、每次调用的输入和产物”，供运行时间轴、节点表、来源链路和本次运行 DAG；DSL 只是记录投影，不是可编辑定义或第二权威。[H #b9cdb477，04:03:07](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/b9cdb477)。这是兼容用户方向的解释，节点/边具体建模不是同条用户逐项指定。

**(D)** 当前 `design/layers.md:40-43` 保留图、刷新、未走完运行和介入入口；`design/store.md:84` 明确捕获为节点、输入列表为边，不另设 DSL。

### D2. store 是可落盘的状态管理，前端不需要额外 DSL；agent 对话不因此变成 soroi 状态

**(U)** 最明确、后于 D1 的用户裁决：

> 通常来说，以omp的视角来看，store天生是session log，但是，如果store不是session log，而是能落盘的状态管理，则直接解决后期复用，值怎么存储，捕获，前端连dsl都不要了

证据：[H #64246eaf，05:07:53](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/64246eaf)。

**(A)** 助手随后将其解为“直接订阅 store”，而非从日志翻译图；同时将 transcript 留给 omp，store 只引用 session id，不复制对话。[H #4db8ea45，05:08:14](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/4db8ea45)。注意此条助手当时说“值是节点”，当前文档说“捕获是节点”，不可把两种画法混为一项用户定案。

**(D)** `design/store.md:23` 与 `:84` 已分别写明 transcript 归 omp、GUI 直接读 store；`design/layers.md:38` 指向 store 的读取章节。该核心意图已经保留。

### D3. 历史时间轴是核心能力，不是可有可无的展示索引

**(U)** 用户在助手将时间轴列为对象快照存储的代价之后直接强调：

> 历史时间轴是个极为重要的功能

证据：[H #9ff9d2be，05:25:49](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/9ff9d2be)；前文助手把读取历史说成沿快照链或派生索引：[H #a74ac1d7，05:24:18](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/a74ac1d7)。

**(A)** 后续助手在 DuckLake 方案中修正：事件表是时间轴权威；快照只做一次查询的一致性，不能承担永久历史。[H #59379f22，05:33:14](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/59379f22)。用户没有逐项指定事件表 schema，不能将其全部标为 (U)。

**(D)** `design/store.md:72-80` 当前保留按运行与递增序号查询、按 k 回看、快照可过期而时间轴不依赖快照；`design/layers.md:40-41` 保留运行图起止时间和刷新。这部分方向一致。

### D4. 运行中的远程数据本机落盘，结束后汇入中心；实时查看不能假装中心已有这些数据

**(U)** 用户决定：

> 我认为ducklake没有太大问题，部署非常方便，然后我认为其实还有更优雅的解法，我不知道ducklake能不能这么做，对于运行中的数据，实际上他们各自是独立的db，而只有运行结束后，才会随着拷贝一起回集中副本，根本没有并发不并发写入的问题，而写入这事，本来就应该本机落盘，而不是，有一堆集群，维护一个中央的数据库全写一个库

证据：[H #8e0a7e8f，05:35:38](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/8e0a7e8f)。

**(A)** 助手紧接着明确：运行中的图、产物写入进度和“现在”线经网络层只读本地库，汇入后读中心；运行中计算的结果在汇入前不能供其他运行复用。[H #fecb24a3，05:36:18](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/fecb24a3)。

**(U)** 用户随后说：

> 我认为差不多都敲定了，先写文档，同时开subagent去调查你还没调查的部分

证据：[H #bfd6975c，05:37:17](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/bfd6975c)。这是对紧邻方案的总体收敛，可支持主路径方向；不能宣称用户批准了后来每一项网络推送技术细节。

**(U)** 后来又收紧：

> 你以为这样改就能了事？从store拷入运行环境都来了，eval禁止递归嵌套，eval永远只有中心主机能运行

[H #5a37a640，08:25:02](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/5a37a640)。因此上述早期助手 #fecb24a3 中“eval 主机也和远程一样结束后统一汇入”的延伸不能继续采用。

**(D)** 现状：`design/store.md:54-69` 限定为远程 agent 批次目录 → 写回 → 中心副本，`:78,85` 区分中心运行事件与远程进度两路读取/推送；`design/eval.md:166-168` 明确 eval 中心运行并直接提交。这些边界总体已修正。

### D5. draft/dry run 不能被混成已进入 store 的未来完整图；正式运行一步一步长出程序

**(U)** 最新明确限制：

> dry run根本没有store，eval里一个atom什么时候叫成功运行还需要store？

[E #32b6f7fd，08:54:56](session://01a18e8a-ba9d-76af-acd2-8e12765ec3e4/entry/32b6f7fd)。

> eval的过程存在dry run，这个阶段不写store，和整个eval的atom从哪来到哪去，是你妈逼两件事

[E #a45ac248，08:56:18](session://01a18e8a-ba9d-76af-acd2-8e12765ec3e4/entry/a45ac248)。

> eval里所有的正式远程运行才需要进入store，任何非正式运行从头到尾都不进store，否则为什么叫非正式？

[H #7ffcea0c，08:30:15](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/7ffcea0c)。

**(U)** 一点一点写出程序的原始目的：

> 但是为什么我一开始想要eval，的核心，是模型可以不要一下子把所有东西全写了，而是一点一点写出来，所以有atom提醒，他完全可以一次只写一个值的消费

[B #4986c617，07:08:25](session://01a18ed5-5798-704f-aa9f-c28be4023631/entry/4986c617)。

**(D)** 当前 `design/store.md:7,84` 和 `design/eval.md:48-51,149-155` 正确写成：dry run 不入 store，未走完的运行画已正式运行的步与未消费 atom，整份程序是正式运行过的步。这里的“草稿”已不是最早助手所说的“store 中预存全部未运行捕获”。

### D6. GUI 写入不是合并修改旧值；人类介入产生新 atom / 新运行

**(U)** 用户先纠正“只有 AI 写”：

> 不，写方不一定只有ai，可以是人在gui写，写了以后通知ai改变了，但是值已经进去了，这个写是这样的，原本是soroi就有暂停运行然后改了重跑，等于是仅更改输入值后跑同样的preset，这对于现在来说是一样的，新的实例，新的参数，旧的函数体，所以要写的东西比你想的要多

[H #ba5ad307，05:16:25](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/ba5ad307)。

**(U)** 又直接否定合并写：

> 我觉得合并写入是不对的，人类写这种操作等于，将一个运行的程序取消，原本的atom要经过程序消费，现在经过一个特殊的程序，就叫他人类接入，所以产生了新的atom，然后自动触发函数消费

[H #d1baf561，05:18:56](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/d1baf561)。

**(U)** 正式运行与介入的最新约束：

> eval因为明确存在正式运行，正式运行同等于固化，所以才有人类介入的可能性，人类修改正在运行的函数体并派生新的闭包这件事永远都是正式运行

[H #a0d22b8a，08:32:02](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/a0d22b8a)。

**(D)** `design/layers.md:43,64-65` 和 `design/store.md:7,18` 已以介入文档链接、只追加、派生运行承接。读取视角下，应保留原运行可回看与新运行来源，而非 GUI 原地覆写图。

### D7. 用户确实要求能比较多路结果，但“跨运行按哪个键对齐”不是已经被用户钉死的规则

**(U)** 并发实例与结果比较的实际诉求：

> 实话说，不如不用import export，直接回到原本的类型层上做，因为要拿到多个实例很正常，我并发开五个验证同一个东西，然后我要比较这五个，这怎么写？

[E #4da22ab4，06:43:16](session://01a18e8a-ba9d-76af-acd2-8e12765ec3e4/entry/4da22ab4)。

**(U)** 后来强调下游必须知道同名结果对应谁、算法与参数是什么：[B #ea638181，07:22:25](session://01a18ed5-5798-704f-aa9f-c28be4023631/entry/ea638181)，原话：

> 接下来还有更复杂的问题，假设，我输入五个参数，中间并发五个不同的步骤，他们的核心意义是，使用了五种不同的算法，去处理这些东西，而其中这五种算法各自需要的参数都不一样，最后产生了五个同名结果，如何指代谁是谁？下游如何看见这些值知道我要干什么

**(D)** `design/layers.md:34` 是“两次运行可以比较，按调用对齐逐项比较产出”，`design/store.md:50` 仅说 SQL 适合比较，`:15-16` 提供步/捕获信息。

**(A)** “两次运行按身份对齐”来自助手 [H #4db8ea45，05:08:14](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/4db8ea45)，不是上述用户原话。用户这里的五路比较也不等于已经决定五个独立 run。两者需分清，不能从比较诉求推导出未裁决的 run 划分与对齐算法。

### D8. 运行开始/结束对外可见已有文档要求，自动化是业务消费方；尚无更细用户事件协议裁决

**(A)** 在用户要求全面理解业务后，助手报告原型自动化 A-01：当实验状态变为“已结束”，且至少绑定一个讨论，由“智能体·复盘撰写”生成复盘草稿。[H #8cb36f90，04:00:29](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/8cb36f90)。这是历史助手读原型的报告，不是本次直接观察原型，更不是用户逐字设计事件协议。

**(U)** 用户要求把待补层写成要求而非马上设计方案：

> 然后，再写一个文档，soroi要补什么设计层要实现什么，其中特别是，远程运行和远程捕获，这是要求，不是现在立刻写怎么实现和方案

[H #85b259a5，04:05:05](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/85b259a5)。

**(A)** 助手在产出的层要求摘要中列“运行开始和结束能被外部看到，供自动化触发”。[H #38659947，04:07:29](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/38659947)。

**(D)** `design/layers.md:67-69` 正是外部可见开始/结束供自动化启动新程序；`design/store.md:19` 有运行开始/暂停/继续/中止/结束，`:85` 有订阅运行变化。支持“事件必须能被消费”的现有要求，但本次已读用户消息未直接定义 event API、开始/结束的确认者或自动化触发实现。

## Rejections

1. **(U) 不再需要为 GUI 留一个额外 DSL。** 早期 #47b71e05 允许记录导出 DSL，后期 #64246eaf 说“前端连dsl都不要了”；这是演进，不是两个并列方案。当前 `store.md:84` 已切到后者。[H #47b71e05](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/47b71e05)、[H #64246eaf](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/64246eaf)。
2. **(U) 不把 GUI 人工修改当成多写方合并旧值。** “我觉得合并写入是不对的”，明确改为人类接入消费与新 atom。[H #d1baf561](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/d1baf561)。当前 `store.md:7` 一致。
3. **(U) 不把 dry run 的未运行/试验节点写进 store 以满足草稿渲染。** “dry run根本没有store”“非正式运行从头到尾都不进store”。[E #32b6f7fd](session://01a18e8a-ba9d-76af-acd2-8e12765ec3e4/entry/32b6f7fd)、[H #7ffcea0c](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/7ffcea0c)。因此最早助手的“未求值捕获在 store 里是未运行节点”不能作为现行 GUI 主路径。
4. **(U) 不做跨运行 atom 消费来方便旧值装载/GUI 关联。** 用户明确：“跨会话消费从头到尾就是错的，听不懂？难道要开好几个atom互相看见atom？那我拆你妈库呢”。[H #63f31453，08:18:31](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/63f31453)。当前 `eval.md:41` 用运行边界表述，`layers.md:31` 的“查看和装载”只能按查看记录/文件理解，不能反向变成跨运行 atom 可见性。
5. **(U) 不为搜索把结构化记录先二进制存一份，再完整复制进反向索引。** 用户：“如果，数据本身还要再在数据库里存一遍反向索引，等同于又写了一遍，那么原始的我二进制数据反而没有啥意义了，不如一开始就是搜索引擎”。[H #543f0ccd，05:29:58](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/543f0ccd)。当前 `store.md:37,43-46,86` 已不单独落盘结构化二进制，但 FTS 文本派生表是助手后续技术折中，不要误称用户明确批准的原始要求。
6. **(A) 没有证据表明用户禁止所有 AI 自主修改或要求 GUI 永远只读。** 助手自己在 [H #54445cdc，04:00:36](session://01a18e1f-5cf2-7281-bf9a-03d102b315ba/entry/54445cdc) 更正：“AI 从不直接改东西”只是原型观察，不能提升为硬规则；随后用户还明确 GUI 可写并转为介入。该助手自我更正不是用户直接拒绝，列在此防止重新引入被其撤回的解释。

## Open questions

## 交接结论

**(A, [INFERENCE])** 当前文档已经保住最重要的转向：**GUI 直接读取持久化 store、不额外 DSL；历史事件表独立于临时快照；正式步骤逐渐形成图；人工介入不覆写旧运行；远程进度与中心记录分别读取。** 证据是上述 (U) 明确裁决及对应 (D) 段落，而不是现有实现。

**(A, [INFERENCE])** 主要未闭合点不是“要不要 DAG/live updates/比较/自动化”，而是 **业务草稿的准确含义、run 生命周期锚点、跨运行调用对齐、自动化事件消费归属，以及远程可见性文字与在途图信息的读取契约**。本报告只识别缺口，没有设计新状态模型或写代码。
