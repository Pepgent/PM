# D15 Steady 审查

## 结论

**整体立场：有条件。** D15-00、01、02、04、06、07、09、12、13、14 的方向可成立；D15-03、05、08、10、11 在当前文字下不能直接进入执行。最严重的不是技术方向，而是三类可执行性缺口：

1. **D15-03 把“曾在发布前取回 49 个当前正文”误写成“会话 transcript 中已有 49 个会话前正文”。** 现有证据只证明发布程序曾取回正文并成功 PATCH；没有证明 49 份旧正文全文已持久记录在 transcript、PM 或其他可恢复权威源中。当前 GitHub body 不能重建旧版本（`R05.md:107-108`、`S4.md:280,316`、`INDEX.md:1247`）。
2. **D15-05 没有把所有脏工作树与分支逐一分成“确定为本会话污染”“确定为会话前遗产”“归因不明”。** 直接执行“会话中新建 worktree 移除/会话分支删除”会把归因未明的 staged/dirty 内容一起销毁；这与 D15 自己的“不猜”、V-5/VG-2 及 `LEDGER.md` C5-3 冲突（`INDEX.md:730-760,976-1005,1078-1081,1220,1240`）。
3. **D15-11 把所有“代码任务”逐项送三族表决，扩大到已通过契约内的私有实现，和 `LEDGER.md` C2-1、`AGENTS.md:50` 正面冲突。** 需要表决的是重做的决策、公开契约、派工边界、issue 验收正文与设计回写；已通过契约内的单仓私有代码结构/算法仍应由工程师决定。

另有一个必须在执行契约中写清的共同条件：各仓 revert 必须**按该仓 main 的逆拓扑/最新到最旧顺序**执行；遇到重叠文件冲突时，不得把冲突解决成“当前正确版本”，而必须以 05:48:24Z 的该仓树状态和明确保留的合法遗产为目标。草案目前只写“按仓 revert merge”，不足以约束 soroi、PM、Pepgent 等存在连续重叠提交的仓库。
