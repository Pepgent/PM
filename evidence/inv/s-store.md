**最重要的结论：**

1. **(U)** store 的方向是“能落盘的状态管理”，而不是 omp transcript/session log；用户明确把复用、值、捕获、GUI 免 DSL 联系在一起。S `#64246eaf`，10-31 05:07:53。
2. **(U)** DuckLake 的主要目的不是中央数据库高并发，而是**远程 agent 本机独立落盘，结束后随拷出回集中副本**。S `#8e0a7e8f`，05:35:38；`#3dbd0473`，08:27:31。
3. **(U)** 必须按后来纠正收窄：eval 只在中心主机；远程 agent 不能再开远程 agent；dry run 从头到尾不进 store；不存在跨运行互相消费 atom。S `#63f31453`、`#5a37a640`、`#3dbd0473`、`#7ffcea0c`；E `#32b6f7fd`、`#a45ac248`。
4. **(D+A) [INFERENCE]** 当前 `store.md` 主方向基本符合上述纠正，但**服务进程归属、派生运行的变更记录、复用发生在当前运行的记录表达、全文索引重复文本的取舍、身份所覆盖的依赖**仍只有半截。具体见下文逐项证据，不能把这些缺口当作用户要求添加 daemon、分布式一致性机制或完整事件溯源架构。
5. **(A+D)** “soroi 服务”确实被 assistant 当作中央写入/汇入/通知执行者提出，当前文档沿用其名字；**没有找到用户决定它由哪个可执行程序、插件进程或独立组件拥有**。它不是已证实存在且有清晰生命周期的服务，亦不能由此推导“必须重建外部控制面”。详见服务归属节。

## Decisions

### 1. 不可变中间值，实际输入输出捕获，消费可以分支

- **(U)** S `#f1ad9522`，10-31 02:41:01：
  > 第二，另一个核心宗旨是，假如我们是一个纯函数式语言，没有变量，只有定量，必须不可变，那么程序中每一个中间结果实际上，都可以被状态管理捕获，就类似jotai
- **(U)** S `#edbaf573`，02:42:12：
  > 一种类jotai中间件他负责程序中非agent的部分的捕获，这次输入了什么，输出了什么，而因为他是中间件，所以可以处理非本机的文件捕获
- **(U)** S `#49e6867a`，02:43:29：
  > 而，agent的捕获，是纯粹的 自动以工具行为，就比如subagent在omp中必须调用yield返回给主agent信息。那么自定义工具，直接接受subagent给的文件路径，就等于捕获运行时产物，而这个类jotai的中间件，自己完成整个传输和管理部分。
  此处的 `yield` 是当时举例，后来的 subagent 决定已改成不走 yield；此报告只采用“路径交回与中间件传输管理”的 store 含义，不能把例子固化为接口要求。
- **(U)** S `#46e29915`，02:50:10：
  > 那么，我们能不能指定一种规则，atom必须被消费，也就是pure类型必须再一次被消费，而这个消费只有两种可能，一种是捕获，一种是停止。而为什么会有捕获，是因为，运行了一段程序
- **(U)** E `#cab573e1`，06:33:37：
  > 我只是说表层是这么做，没说底层不套类型，否则这个值怎么派生，并且没有人说值不能分支，一个参数可以被五个不同的地方消费，那每一次消费都是派生新的值
- **(D)** 对应当前 `design/store.md:7,13-21`：只新增、不修改，值/捕获/停止等记录；消费关系不另存。**后半句“具体如何用捕获输入表示消费”是文档的设计细化，不是用户逐字段规定。**
