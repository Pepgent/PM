# 工作量与时间分布取证（LensEffort）

## 结论摘要

目标会话 `01a193fd-e992-76d2-8c29-060fe52cc094` 的真实用户任务窗口为 **2026-10-31 22:14:14.883Z—2026-11-01 05:48:20.203Z，共 7 小时 34 分 05 秒**。它先组织历史意图/仓库/harness 调查、Argon 与决策治理，再启动独立工程师和测试者，后期主要接收消息、裁决契约、转述进度并等待；最后约 23 分半转为响应用户纠偏、停止工作者与重派分析。

有意义的总体发现：

1. **不是“几个小时完全没做事”。** 实际启动了 10 个产品工程/测试独立进程；首批 25 个调查者有完整回报。用户本来明确要求领导团队、秘书、调查、意图守门与全流程，因此这些事务本身不能定为浪费。
2. **主会话确实主要在编排而非实现。** 全部 670 个带工具的事件中，等待、内部消息、peer 消息/列表及派遣合计 486 次（72.5%）。`wait` 174 次，记录耗时 2:44:33，占任务墙钟 36.2%、记录工具耗时 97.6%。这些时间很可能与工程师工作重叠，不能说是全团队空转。
3. **存在小而确定的重复动作，也存在持续的管理回路。** 初期四次调查派遣被拒后才成功；01:33 连续 `wait` 在“Nothing to wait for”之后仍继续一次，随后改正；05:00 前后对同一轮 55/16/37 状态连续多次播报。后者与用户“领导分身处理、主领导专注推进”的优先级有张力，但不能将全部管理时间算作无效。
4. **交付优先级最终没有兑现。** 主 agent 自述在 01:34 时 27/108 切片合并、0/32 完整流程通过；约三小时后治理上报 55/108，但最基本 live F01 仍待 STO-05；05:03 又从真实 root 入口发现首条模型请求的 schema 400。上述记录支持“局部成果不断增加，而完整可用路径长期未形成”，不支持在本次权限内断言其唯一原因是 monorepo。
5. **不能从 root 静默反推出所有 AI 都在等待。** 任务内有 14 个 ≥5 分钟的相邻事件静默区间，合计 1:51:23，最长 14:55；不少结束于工程师来信。没有读取独立工程师会话，也没有 Git/GitHub 授权，不能量化实际工程工时、重复验收工时或仓库合并的因果成本。

## 一、统计口径与可复现性

### 来源与边界

- 元数据：`session://sessions.jsonl?q=select(.sid|startswith("01a193fd"))`。状态 `aborted`，created `2026-10-31T22:04:13.586Z`，modified `2026-11-01T05:48:20.203Z`，文件大小 11,904,191 字节。元数据的 `assistantTurns:3` **不是 events 的轮次统计**，本报告不用它代替事件轮次。
- 主数据：目标 `events.jsonl` 的全部 1,514 个活动分支事件，未只抽样某一时间段。
- 子 agent：主事件中的 `dispatch`/`subresult`，以及目标 `agents/` 列表。不把外部 tern 进程当成本会话 task 子 agent，也不读取其独立 session。
- 个别工具结果用目标 `entry/<resultEntry>` 确认。没有运行 git，没有打开 GitHub issue/PR，没有修改仓库或外部状态。
- 时间均为 **UTC（Z）**；跨日后省略日期的表格明确说明。

### 三种时间不能相加

1. **墙钟跨度**：两条时间戳的差。它包含模型生成、工具、等待、外部工作和静默。
2. **记录工具耗时**：`durMs` 的和。抽查实际结果，例如 #2d1d6add 的 `startedAt` 与 call 事件时间只差 1 ms，能确认该字段是工具实际执行记录；但同一 assistant message 的多个工具共享事件时间，因此不据此捏造严格互斥的全程利用率。
3. **子 agent 回报 duration**：某次工作/唤醒到本次回报的运行包络，不是 CPU 时间，不是唯一 agent 的总寿命；同一 agent 可多次回报，多个 agent 可重叠。所有回报 duration 求和仅作“已报告运行包络合计”，绝不与 root 或 tern 工时相加。

`turn` 是事件提供的轮次标签，不保证不同轮次的事件时间包络严格不重叠。只有用户事件的一轮跨度为 0，**不表示 agent 立即完成了用户要求**。相邻事件静默也只表示 root 未记录事件，不表示整个集群 idle。

### 核心 jq 复现表达式

将以下过滤器放入目标 `events.jsonl?q=`（`&` 如需出现应编码），即可复算主要统计：

```jq
[., inputs] as $e |
{
  kinds: ($e | group_by(.kind) | map({kind: .[0].kind, n:length})),
  tools: ($e | map(select(.tool)) | group_by(.tool) |
    map({tool: .[0].tool, n:length, ms:(map(.durMs // 0)|add)})),
  turns: ($e | group_by(.turn) |
    map({turn: .[0].turn, first:(map(.t)|min), last:(map(.t)|max)}))
}
```

本报告轮次秒数由时间戳截至秒后相减，精度约 ±1 秒；总体任务窗口另按完整毫秒计算。工具和子 agent 时间保留原记录精度。

## 七、如何理解这些统计，避免过度裁决

- **能支持**：主会话主要花在编排和等待；初期确实开展了用户要求的调查/组织；独立工程师真实启动；存在少数明确短循环和后期反复转述；完整交付长期落后于局部切片完成。
- **不能支持**：“7个小时都是空转”“174次wait全是无效”“没有任何功能”“所有AI都在等”“monorepo必然导致全部延误”。用户关于低效与等待的观察应按真实问题对待，但其具体耗时拆账需工程源头证据，不能由审计者凭感觉补数。
- **接回正轨的工作量方向**：复用已有调查、决策和已实现代码；核清被停止者的实际产物；把领导注意力从逐条ACK与状态复述转到剩余关键依赖和共同决策；遵循用户后来明确的实现→完整E2E顺序，最终以全流程结果而不是数量收尾。这里只给工作编排建议，不新定产品架构。

## 置信度与未覆盖部分

- **高置信度**：root活动分支1,514事件、670带工具事件、各轮包络、174次wait及记录耗时、消息/工具分布、14段任务内长静默、成功dispatch/回报数量、实际tern启动及停止输出。
- **中置信度**：按intent和时序归纳的事务性质、与“专注推进”的张力。它不是严格互斥的工时记录；根模型生成时间未单独计量。
- **只作为agent说法**：合并/Done数量、0/32验收状态、某次外部运行的详细结果。它们出自目标会话的主agent或来信，未当作本调查亲自复验的GitHub/运行结论。
- **未覆盖**：全部嵌套子agent总数与完整工时；10个独立工程进程各自实现、等待、测试、重跑的分布；各轮决策反复投票的完整子事件统计；仓库/CI成本及monorepo因果评估；被停止工程进程最终代码现状。前两项没有读取独立session的权限；Git/仓库历史与GitHub事实**需 git/GitHub 授权才能确认**。
- 本调查未修改仓库、未运行测试或复现产品行为、未使用hash作为证据。导师只评估了统计口径与推理边界，不是独立事实验证者。
