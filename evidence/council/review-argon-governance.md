# Council daemon 方案审阅 — ArgonGovernance（组织治理席）

## 1. 结论与审阅边界

**结论：支持 daemon 方向，当前稿“有条件通过方案方向，但不能按现稿原样实现并宣称落实 U104/U105”。** 可行性报告已经提供并发记票、事件流过滤、idle 席位自行被唤醒、launchd 托管与 GitHub issue/Project 写入的机制证据。它也实证揭示了 park 后订阅死亡，而不是证明了常驻席位全生命周期已经可用。组织上必须先确定以下主路径修正：

1. T3 选 **(a)：让需要持续订阅的角色不因 idle 被 park**，不把 (b) 的 Main 代唤醒列为自动退路。Main 只负责初始进场和重启后的角色重建，不为每次投票复活席位。
2. T9 **将全部投票与议题管理事务交给 daemon，但设计文档仍由 Argon 负责**。不能以“秘书职责收缩”为名把设计维护转给秘书。
3. 参投与治理否决资格不能只由 `category === 治理` 决定；必须按条目涉及的职能领域确定，避免用“技术/实现”标签排除组织治理席。
4. 按席位执行 P0→P3 的确定性处理顺序，不扩张成“前一议程全部结案/归档，下一个才可办理”的全局锁；**已通过行应直接通知片区经理，不等整案结案**。
5. Main 批量读普通状态；常规的跨仓已合入通知应由相关片区经理直接订阅、送达，不能一概包装为 `alert` 重新逐条唤醒 Main。

这些是对方案中现有主路径的选择与纠偏，不是要求重开一轮常驻巡检、增加逐步验收锁，或把 U104/U105 是否执行重新提交表决。U104/U105 的指令本身已经确定；需确认的是实现取舍与既有角色边界。

本轮仅审阅并写本文件：没有修改代码、规则、角色、设置或既有方案，没有提交，没有运行或编写测试，没有启动定时唤醒或巡检，没有查看 git、历史会话或 GitHub issue/PR 历史。

## 4. 应保留的角色分工与生命周期

这次变更应当删除人工搬运，不重造一个拥有所有责任的新秘书或新 Main：

- **工人**：在原 issue/PR 写工程事实；不因采用 council 就要求每名工人另学一套领导层投票系统。
- **片区经理**：观察本仓、记录来源及时间、发布状态；订阅本仓裁决和相关依赖就绪，实际 `tern send` 并观察工人恢复。不能为了发一条上游就绪通知先等待 Main 转述。
- **提案职能席/治理承接者**：直接向 daemon 提交决策行、实质分类与理由；不先经过秘书或 Main 审批。治理承接者依 U103 每项新开、办完即结束，其票仍归 Coordination 一席。
- **Argon / ArgonGovernance**：BLOCKED 的 A/B 正交边界把关不因引入 daemon 而消失；由程序记录和传送，不把程序当成能替代人判断产品意图或治理边界的裁决者。常规白名单内工程不新增这道事前锁。
- **LeadMentor**：只处理职责内的终局分类争议，不替程序核账，不被强制等齐无关选票后才看到已存在的争议。
- **独立审查席**：每案空白实例、完成即结束；steady/divergent 可以产生两份审阅材料，但按现行规则合计仍只有一个独立审查席位票，不能因为存在两个实例而加票。
- **独立职能部门**：保留直接提案权、专项参投和自身非例行事务边界；daemon 不把 SoroiKeeper/OmompOptimizer 默认改成每案都要回应的常规支撑席。
- **Main**：初始派活、席位轮换、实质排期与 Coordination 票；读批次摘要。不承担席位逐次唤醒、选票转录、计票广播或裁决逐条转述。
- **daemon**：受理、顺序、版本、记票、机械计票、发布、事件流与归档。它管理的是议题和记录，不取得对工程代码、设计意图或进程是否恢复的解释权。
- **Secretary**：退出已经自动化的重复职责，保留非决策记录事务。不把“保留一个人盯住每次 outbox”当作运行主路径，不逐分钟刷新 LEDGER。

**每行形成可执行结论 → 通知相关片区经理 → 片区经理送达并观察**，与 **整案结案 → GitHub/Project 更新 → 归档** 是两条不同依赖链。前者不能嵌套等待后者全部完成。Argon 回写设计、秘书回写索引与已授权工程执行也应并行，不重新引入 U83/U88 禁止的文书等待。

## 5. 可复现的主路径失效反例

### CE-1：正常 idle 后，投票又依赖 Main 代唤醒

**来源：** design §10.2/T3；feasibility §5 的 park 实测。

**[INFERENCE] 步骤：**
1. 用现行 420000 ms 设置启动常驻席位，挂 watch/monitor 后结束本轮。
2. 正常空闲超过 7 分钟。
3. 授权提案者提交该席必须参投的新案。
4. 方案若选 T3(b)，daemon 只能发 `seat.unreachable` 给 Main，再由 Main `write agent://` 恢复该席；不做这一步就收不到票。

**失效点：** 不是异常输入或竞态，而是常驻岗位的正常空闲生命周期。票的内容虽未走 IRC，投票推进仍以 Main 的逐次主动唤醒为前提；U104/U105 的去总线目标没有完整实现。现有证据已经足以要求选 (a)，无需再做一次同样的 park 实验。

### CE-2：已通过的工程解阻行被同案无关争议扣住

**来源：** design §4.1 的整案状态、§6.3 的 `agenda.decided`、§7 的片区经理送达路径。

**[INFERENCE] 步骤：**
1. 一案包含两行：R1 是某工人的解阻，R2 是另一项可独立讨论的治理条目。
2. R1 已获本行所需选票、达到门槛，无反例或否决，状态 `passed`。
3. R2 存在有效反例，保持 `contested`。
4. 整案不进入 `decided`，设计规定给 R1 片区经理的通知只有 `agenda.decided`，故经理得不到这条已通过行的订阅通知。

**失效点：** 主路径把逐条表决变成整案放行锁。若经理改为反复主动查询，便破坏所承诺的订阅主路径。修正是让已通过行及时经同一事件流通知其 `notify` 收件人，不加秘书/Main 转发，不等整案或归档。

### CE-3：技术标签剥夺组织治理席参投与反设卡权

**来源：** design §4.1 仅治理分类加治理席、仅治理分类允许治理否决；AGENTS D1-12、U90/U95。

**[INFERENCE] 步骤：**
1. 提交一条“以 CLI 技术实现席位生命周期/管理层消息流变更”的工作流条目，正常标注 `category: 技术`。
2. 即使 `what/how` 实际改变岗位职责或引入 Main 转发环节，程序仍只生成四基础席的资格。
3. ArgonGovernance 不是资格席，不能按职责投票，也不能对反设卡问题行使治理否决。

**失效点：** 起草者的单标签取得了划定治理权限的能力，与按职能划分的制度相反。应按条目实质领域确定治理席资格，而非强迫所有涉及治理的技术条目都失真改名“治理”。

### CE-4：正常结案后把设计维护派给无权修改设计的人

**来源：** design §10.1、T9；secretary.md 第 32 行；AGENTS D1-12/C2-1 与 U1。

**[INFERENCE] 步骤：**
1. 某案通过，按 §10.1 给 Secretary 发 `agenda.decided`。
2. Secretary 按方案去回写 `design/`。
3. 若执行，就违反秘书“不改设计文档”的职责及 Argon 的设计维护归属；若遵守角色定义拒绝，就没有方案明确的正确设计回写承接者。

**失效点：** 主路径本身分工冲突，不是秘书不够主动。应把设计回写送到 Argon；秘书只处理明确授权的索引/记录，且不阻塞工程。

### CE-5：常规依赖进展全部升为 alert，Main 仍逐条处理中转

**来源：** design §7 将“跨席位前置合入”统一归 alert、§6.3 alert 全送 Main；U104。

**[INFERENCE] 步骤：**
1. 上游连续完成若干已经授权、无需改排期的前置合入。
2. 片区经理完全按方案逐次 `status post --kind alert`。
3. Main 的 monitor 每次命中；而下游实际送达仍须回到片区经理办理。

**失效点：** 内容原本只是常规依赖就绪，却更换包装继续逐条唤醒 Main。应区分需要 Main 做轮换/排期决定的事件与仅需相关片区经理送达的事实；后者可通过同一 daemon 直接发给受益片区经理，同时入 Main digest。

## 6. 不应暗中新增的门槛

1. **“资格席全部投齐才处理任何结果”是额外同步条件。** AGENTS 明确了参投范围、专责权与 ≥3/4 门槛，design §4.1 则把投齐作为否决、反例、仲裁等所有动作的统一前置。至少争议/反例通知与导师仲裁不应等无关席位投齐。是否必须收齐所有必投席回应才能最终落槌，应明确对齐现行席位参与要求，而不是由代码不声不响新增或删除门禁；不能为求快绕过 Argon 的必需参与，也不能把普通迟回应变成阻断一切通知的理由。
2. **非空反例不等于有效反例。** CLI 校验字符串只证明有文字；有效性仍由既有职能判断并留据。不能让程序把任何非空反对永久升级为必须修改条目才能解除的事实否决。
3. **issue 发布、归档和设计索引回写不应成为额外工程许可。** 已有合法结论按既定阶段与白名单送达即可；归档另走自己的结束锚点。
4. **不替每个技术问题增设治理席。** 本审阅要求修正真实治理领域漏权，不要求把所有工程细节强制五席参投。
