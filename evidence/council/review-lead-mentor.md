# 议会 daemon 独立导师席审阅

审阅者：ReviewLeadMentor（独立导师席）。本轮为一次性方案审阅，不是正式 decision issue 的计票或分类争议裁决；本文不自行创设规则，也不修改代码、角色定义或现行规则。

## 一、结论

**架构方向赞成；具备落实 U104/U105 的技术基础，但当前文本尚不能原样作为完整实现契约。** 建议保留单 daemon、SQLite、CLI、launchd、GitHub 发布面与 `watch + monitor` 的总体结构，补齐下述四处正常业务路径后实现，而不是另造架构：

1. 确定性排队须约束实际投票入口，不能只控制发通知的次序。
2. 按行决定资格席位，但不能仅凭互斥的 `category` 字段识别治理参与，也不能遗漏非发起方的全局产品架构参投席。
3. 分类争议须能独立于否决票提出，并抵达导师席；不能只有已投齐后的否决才触发仲裁。
4. 对反例以源头实证完成反驳后，须有记录其处置结论并重算的业务路径；不能只剩修订、撤回、反对方改票。

**T3 选择关闭常驻订阅者的 idle park，而不是依赖 Main 的 IRC 唤醒或新增 relay。** 只延长有限 TTL 不满足长期订阅的主路径。实施时还须覆盖秘书、需要接收裁决的片区经理等常驻订阅者，不仅是投票席。

U104/U105 的执行本身不交付投票决定是否采纳。依 AGENTS.md C2-4，不能把“是否由程序接管投票、议题和 issue 写入”“是否取消 Main 常规状态总线”重新作为可否决的选项。本轮审查的是落实方式及其是否忠实承载现行制度。

## 三、T1–T9 逐项意见

## 四、具体主路径失效反例

以下是依方案文字可逐步推出的正常业务路径反例，不是本人已执行的 runtime 结果，也不涉及异常输入、竞态、重试或恢复设计。

### CE-1：只排序通知，不能保证按序表决

- **位置：** `design.md:196–202`、`243–251`、`321`。
- **场景：** 一个席位尚未投完 P0 议程，同时存在 P3 议程。该席从正常查询取得 P3 编号，直接执行方案已有的 `council vote <P3议程> ...`。
- **推导：** 当前明确描述的入口检查是“当前在席 agent”，队列规则只说不发下一个 `vote.request`；未规定非队首议程不能投。若按此实现，即使通知顺序正确，P3 仍可先投票。
- **冲突：** AGENTS.md:24–26 要求全体参投席位按确定性顺序表决，而非只按序收通知。
- **最小修正：** 将每席当前可投议程作为 `vote` 与 `queue` 共用的确定性业务规则。不增加全体席位同步结案锁。

### CE-2：资格函数会漏掉法定参投席

- **位置：** `design.md:74`、`99–106`、`158–162`、`339`；对照 AGENTS.md:18–23。
- **场景 A：** 起草一行“将治理事务的 IRC 转发改成程序订阅”，分类标为“实现”，内容实际是工作流与组织分工调整。
- **推导：** 当前函数仅在分类为“治理”时加入 ArgonGovernance，因而只算四席；治理席不能投票或行使其工作流/反设卡专责权。
- **场景 B：** Main 发起涉及全局产品架构演进的技术行，而非 SoroiKeeper 发起。
- **推导：** 当前函数只在发起者为独立职能部门时添加发起席，遗漏现行 AGENTS.md:20、22 所写的全局产品架构参投条件。
- **冲突：** 这是程序资格模型缩减了法定席位，不是可由实现者任意简化的细节。
- **最小修正：** 按行表达适用职能范围与应参投的独立部门，再由规则推导资格与门槛；与五选一的决策分类分开。若“对应产品全景席”的具体指定仍有歧义，方案应明示所采用的解释交管理层确认，不能默认为不参加。

### CE-3：有分类争议，却没有进入导师仲裁的路径

- **位置：** `design.md:136`、`164–167`、`199–200`、`243–245`、`335–337`；对照 AGENTS.md:33–35。
- **场景：** 起草者将一行标为“技术”；Argon 审阅后在分类意见中坚持“意图”，但并不认为该行已达到应行使一票否决的程度，例如暂不支持而尚无可引用的否决依据。
- **推导：** 方案保存了 `classification`，却只为“Argon 对非意图行投否决且资格席投齐”定义 `disputed` 和 `arbitration.request`。因此真实分类分歧存在，也不会触发仲裁。
- **冲突：** D1-17 将“坚持归为意图”的分类争议交导师终局仲裁，不以提交否决票为前提；默认技术是争议期间的默认，不是吞掉仲裁请求。
- **最小修正：** 在现有分类意见/仲裁命令上补齐明确的分类争议发起和送达语义，保留导师决定的记录；不要求额外审批机构或模型自动裁意图。

### CE-4：实证反驳不能清除 contested

- **位置：** `design.md:164–168`、`190–208`；对照 `decision-vote` 第 38–40 行，以及 AGENTS.md:27 的“有效反例”。
- **场景：** 一行收到具体反例，随后发起人用源头实证证明该反例与现行条目不符。条文本身无需改动；反例处置已经形成明确记录，但原反对票仍须作为历史事实保留。
- **推导：** 方案只允许修订新版本、反对席改投或撤回。没有记录反例已被实证反驳并重新求值的入口，正常反例回应无法完成闭环。
- **冲突：** 现行流程允许以源头实证反驳反例；“反例优先”不是任何原始反对字符串都永久拥有阻断效力。
- **最小修正：** 在现有议题管理中表达反例处置及依据，再按有效反例是否清零求值。程序记录有权处理者的结论，不自行裁判实证真假；本意见不授权 Main 单方抹除异议，也不新增一种自动证据裁判机制。

### CE-5：T3(b)/(c) 把订阅主路径重新接回主动消息

- **位置：** `design.md:248`、`310`、`322–326`；`feasibility.md:161–197`；U105 原文在 `LEDGER.md:116`。
- **场景：** 常驻席位按现行 TTL 正常 idle 超过 7 分钟后，新议程到达。
- **现有实证：** 原探针观察到席位被 park 后 watch 进程消失，目标事件未唤醒席位。
- **方案分支 (b)：** 要 Main 接 `seat.unreachable`，再 `write agent://<席位>`；(c) 则新增 relay 做这件事。
- **冲突：** 两者都把正常投票接回额外主动通知；(b) 还使 Main 在日常议程中再次承担唤醒中转。U105 明确选择 daemon 配合 exec command monitor 订阅，而不需要额外主动通知机制。
- **选择：** 采用 (a) 的常驻订阅生命周期；不拿 (b) 当作与用户原话等价的常态备选。对有限提高 TTL，同一个正常场景只需等到新的 TTL 即仍成立。

## 五、实施与交付边界

1. **继续沿用现成结构，不因本审阅增加一轮泛化架构或新消息系统。** daemon 负责自有议会状态与机械发布；席位负责判断、投票和仲裁；片区经理负责实际送达并观察工人恢复。这三层不可混同。
2. **不增加同步验收锁。** 本方案是议会工作台，不得把 daemon 立案、GitHub 发布或归档完成变成正常工程每切片开工、合并和轮换的额外门禁。开发期接缝金丝雀继续异步非阻塞进行。
3. **本审阅不代替所有者修改源文件。** T1、T9 的源头文字切换应覆盖相应角色定义、决策技能与仍引用秘书人工立案/排队的现行指导，避免两个有效入口；历史评论和原票保持不变。
4. **验收使用方案已有的第二阶段完整链路。** 代码完成后，再由实现与验收责任方执行真实 propose → 并发 vote → revise → 重投 → decided → issue/Project/归档，以及 Main 和常驻席位订阅路径；将本次四项业务语义修正纳入该真实议程。本人本轮没有运行这些验证，也没有要求实现前先写测试。
5. **投入生产须区分已证明机制与已交付系统。** 当前可以说“方案的关键技术机制已有可行性证据”，不能说“完整议会 daemon 已验证”。补齐正常路径、实现并完成既定 runtime 验证后，依 U105 立即投入使用，不再附加无关审批或等待条件。

**独立导师席最终意见：赞成采用该总体架构与上述 T1–T9 选择；反对把当前资格、队列准入、分类仲裁和反例处置的缺口直接固化进实现。完成这些明确的方案修正即可推进，不要求推倒重做，不要求将 U104/U105 的用户直接授权重新投票。**
