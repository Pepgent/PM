# 议会 daemon 审阅：产品原始意图席 Argon

## 结论

**主体路线符合 U104、U105；当前稿不能原样作为实现定稿。** 赞成独立 daemon、程序独占写入、并发投票入口、issue/Project/归档自动生成，以及 `exec_command + monitor` 订阅。必须先把 T3 的额外主动唤醒退路、T6 的无 U 意图否决、T9 的设计文档职责转移改掉，并补清 issue 立案与参投资格的主路径。上述是逐项意见，不是对整套方案投一张总票。

**本轮只能确认“机制已有部分可行性证据”，不能确认“全部生产主路径可行、已可投入生产”。** 实现者报告已验证并发收票、issue/Project 写入、idle 席位订阅唤醒与 launchd 托管，也实证了 park 会销毁订阅。受限工具定义、Main 本身的订阅和 Contents API 归档尚未实测；T3(a) 的完整常驻路径尚未给出解决后证据。这些缺口由实现者按 U105 完成，不由 Main 恢复人工转票来替代。

本审阅只读方案、可行性报告、现行规则和 U 原话；未改代码、规则或设置，未运行测试，未查看 git、历史 session 或 GitHub 历史。下述反例为依据文档推演的可复现步骤，除引用的既有可行性报告外，不冒称本席已运行复现。

## 2. 意图裁决

### I1【定】：自动化的是议程事务，不是席位判断

依据 `(U) U11、U12、U20、U105`。daemon 可以立案、排队、验证席位、收票、按既定规则计票、写 issue 和归档；不能自己替缺席席位赞成、裁定用户原意、作导师分类仲裁，或把同一协调席的多个实例分别计票。方案的 `SeatId`、逐行 `DecisionRow` 和 Coordination 合一票方向正确（`D design.md:67–106、156–168`）。两个正反审查实例是同一独立审查席的工作输入，不是两个新增席位。

### I2【定】：订阅不能靠 Main 再发一条消息才成立

依据 `(U) U104、U105`。常规投票请求由程序事件流直接送到实际判断席位；不能以“Main 只负责唤醒、不转述内容”为理由保留逐次主动通知链。T3(b) 明写 Main 用 `write agent://<席位>` 唤醒，T3(c) 只把这项主动通知转给 relay，均不符合本次切换目标（`D design.md:322–326`）。重启时由 Main 初次启动席位，与每次有票时 Main 再发消息是两回事；本裁决不取消正常首次派活。

### I3【定】：数据库作为程序工作源，不等于废除 PM issue 管理

依据 `(U) U14、U20、U105`。赞成 daemon 创建并维护议程、行版本和选票，issue 是其生成的审阅与持久发布面；用户没有指定必须解析 Markdown 当数据库。与此同时，重大事项仍须在 PM issue 中有逐行表格、原票、反例、仲裁与结果。不得用本机数据库的存在替代这些交付，也不能让生产决策只留在本机。

### I4【定】：无 U 的意图意见不得取得否决效果

依据 `(U) U11、U20`。`provisionalVeto` 不应有真正否决效果，也不因换名就自动变成有反例的反对票。`Citation.blockingFact` 可以支持技术反例或主路径阻断事实，但单凭它不能冒充有 U 依据的原始意图裁决。当前统一 `Citation` 直接用于 Argon 意图/缺失设计否决，缺少这一权限区分（`D design.md:121–130、160–166`）。

有 U 的原意冲突判断不能仅因起草者写成“技术”就静默消失；发生意图/技术分类争议，按 U20 进入导师仲裁。导师判为技术后失去意图否决资格，与“没有 U、只能暂定”是两个不同事实，不应在归档中混写。

### I5【定】：秘书事务可自动化，Argon 的本意与设计文档职责不随之转移

依据 `(U) U1、U11、U105`。U105 明确把立案、投票与议题管理交给程序，秘书不再人工收票、计票、维护队列是正确切换；但没有把 Argon 的产品原意判断或 `design/*.md` 维护交给秘书。方案“秘书收到决定后回写设计文档”及“秘书保留设计文档回写”必须替换（`D design.md:304、341`）。秘书可承接非产品设计类事务；产品设计正文仍由 Argon 按已通过条目维护。

## 4. 可复现的主路径失效反例

### CE1：正常等待下一议题，席位订阅消失

- **步骤：** 常驻席挂 `watch + monitor`，结束本轮；没有议题需要处理，正常空闲超过本仓 7 分钟 TTL；此后产生发给该席的 `vote.request`。
- **已有事实：** 实现者报告中该 watch 已消失，事件发出后席位没有唤醒，对照 watch 仍在（`D feasibility.md:161–197`，内含运行输出）。这不是本席另跑的验证。
- **失效点：** 程序只能收下请求，实际投票席不会收到；采用 T3(b) 就必须让 Main 再发 IRC/agent 消息才继续。
- **结论：** 当前配置不能证明订阅主路径成立；(b)/(c) 不符合 `(U) U104、U105`。必须在生产前落实并验证 T3(a) 的常驻生命周期。

### CE2：无 U 的“本意否决”直接击穿多数

- **步骤：** 提案行设 `category=意图` 或 `missingDesign=true`；Argon 用 `choice=veto`，Citation 只填 `blockingFact`，没有 U 编号或用户会话引文；其余资格席赞成并投齐。
- **文档推演：** `Citation` 接受 `blockingFact`；否决资格仅要求带 Citation；状态求值先处理有效否决（`D design.md:124–130、160–168`）。照草图直接实现，会得到 `rejected/veto`。
- **失效点：** 无 U 的意见取得原始意图/缺失设计否决权，而不是暂定意见。实际阻断事实可以成为反例，但不能被程序自动变成“用户曾如此要求”。
- **结论：** 违反 `(U) U20`。这不否认事实反例的重要性，只禁止把事实依据与用户意图依据混为一类权限。

### CE3：起草标签排除本应参投的治理席

- **步骤：** 立案一条改变管理层日常状态上报、读取与唤醒方式的条目；因内容包含 daemon/CLI，把行分类写为“串联”或“技术”；由 Main 发起。
- **文档推演：** 当前资格算法只在 `category=治理` 时加入 ArgonGovernance（`D design.md:158`），其余四席可投齐并达门槛，治理席不在资格集合中。
- **失效点：** 与本次 U104 同类的重大工作流事项，仅因技术实现标签就被排除治理席；与现行 `AGENTS.md:23` 的事项实质规则不一致。
- **结论：** 这是参投算法对已给定规则的漏编码；按 T7 修正。本席把它作为规则一致性与实现意见，不伪称 U12 单独规定了治理席的名字或完整参投算法。

### CE4：按成功决议执行时，错误角色改写产品设计

- **步骤：** 一个含 soroi 产品设计修订的议程通过；daemon 按 §10.1 通知 Secretary；秘书按表格“收到 agenda.decided 后回写设计文档”执行。
- **文档依据：** `D design.md:304、341`；现行 Argon 职责见 `AGENTS.md:17`。
- **失效点：** 程序本身正常工作，却把用户指定给 Argon 的产品设计维护交给秘书，产品意图责任链随自动化被替换。
- **结论：** 违反 `(U) U1、U11`。改为向有相应职责的席位发布结果；“通知设计 owner”不等于“daemon 或秘书代作设计判断”。

## 5. 其他必须明确的主路径，不扩大本次设计范围

1. **反例的处理结果应能进入程序与 issue。** `design.md:167` 仅列修订、反对席改投、撤回三条清零路；现行 `decision-vote` §4 还允许在 issue 中用源头实证反驳反例。应明确这种处理怎样在程序管理的议题中被记录并得到结论，不能让 Main 在 IRC 私下判作“已解决”，也不能把任意非空反例字符串当作永远不能审查的事实。依据 `(U) U20` 的反例优先，具体处理机制由技术/治理席决定；本席不另造 daemon 自动裁判反例真假的权力。
2. **程序生成 issue 必须保留逐行判断所需内容。** `what/where/how/tradeoff`、当前版本、各席原票、U 引用、反例、仲裁与结果应在对应议题可审阅。修订只使受影响行旧票失效，不把其他行已得结论一起抹掉。方案行版本方向符合 `(U) U12`，须贯穿实际入口与发布。
3. **程序上线后的真实生产入口必须就是新机制。** U105 要求实现后立即投入生产；不能把探针演示当生产切换，再继续让秘书 IRC 收票。现行规则正文、角色说明、工具使用说明由各自 owner 同步替换，daemon 管票，席位直接提交，Main 批读。不得要求给 U104/U105 的直接授权再投一轮“是否执行”的许可票。

以上仅覆盖正常立案、审阅、投票、读取、发布与设计回写，不讨论异常输入、重试、恢复、并发竞态或额外安全机制。
